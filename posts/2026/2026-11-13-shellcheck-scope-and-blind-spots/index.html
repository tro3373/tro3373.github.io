ShellCheck が読まない範囲と誤検知する書き方

2026-11-13 ·  2026-11-13 · 14 分 · 2761 文字

結論#

  • ShellCheck は、引数で渡したファイルを実行せずに読み、そこに書かれていることだけで指摘する。source で読み込む先のファイルは、-x か .shellcheckrc の external-sources=true が無いと読まない。読まないと、読み込み先で使う変数に SC2034 (未使用)、読み込み先で代入する変数に SC2154 (未代入) が出る
  • # shellcheck source= の相対パスは、shellcheck を起動したディレクトリ (cwd) から探される。source-path=SCRIPTDIR を付けると、検査するスクリプトのディレクトリから探される
  • # shellcheck disable= がファイル全体に効くのは、最初のコマンドより前に置いたときだけ。コマンドの後ろに置くと、直後の 1 コマンドにしか効かない
  • 終了コードは、severity が info の指摘しか無くても 1 になる。クォート漏れの SC2086 も info である
  • 指摘しないもの: 代入がすべて空白やグロブの文字を含まないリテラルの変数のクォート漏れ、定義の無い関数の呼び出し、zsh のファイル (SC1071 で解析をやめる)、composite action の run: (actionlint が ShellCheck に渡さない)
  • 正しく動くのに指摘するもの: サブシェルの中で定義して、呼び出しが見えない関数 (SC2329)、本体を ( ) で書いた関数の中での変数の書き換え (SC2030 / SC2031)、引数の位置に素のまま書いた done (SC1010)、$( の直後に続けた (( (SC1102)

以下は ShellCheck 0.11.0、bash 5.3.20、zsh 5.9.2、shfmt v3.14.1、actionlint v1.7.12 で確かめた。ShellCheck の出力の末尾に付く For more information: と wiki への link の行は省く。

前提: ShellCheck が読むのは渡したファイルと、追うと決めた読み込み先だけ#

ShellCheck はシェルスクリプトの静的解析ツール (lint) で、スクリプトを実行せずに読み、誤りの疑いがある箇所を指摘する。指摘には SC2086 のような番号 (SC 番号) と、severity (重大度。重い順に error、warning、info、style) が付く。

ShellCheck への指示は 2 か所に書ける。

  • directive: スクリプトに書くコメント # shellcheck <キー>=<値>。disable=SC2034 で指摘を止め、source=<パス> で読み込み先を教える
  • .shellcheckrc: 設定ファイル。directive と同じ <キー>=<値> を書くと、ファイル全体に書いた directive として扱われる。検査するスクリプトのディレクトリから親のディレクトリへ向かって探され、最初に見つかった 1 つだけが読まれる (近い方に空の .shellcheckrc を置くと、親の設定は効かなかった)

ShellCheck が読むのは、引数に渡したファイルと、-x を付けたときの読み込み先だけである。PATH 上のコマンドの中身は読まず、別のファイルで定義した関数は、そのファイルを読まない限り知らない。読まなかった側にある代入・呼び出し・定義は「無い」ものとして扱われるので、正しいコードへの指摘 (誤検知) と、誤りの見逃しの両方が起きる。

source の読み込み先は、-x か external-sources=true が無いと読まない#

source ./lib.sh (. ./lib.sh も同じ) は、別のファイルを今のシェルの中で実行するコマンドで、読み込んだファイルの変数と関数がそのまま使えるようになる。ShellCheck は既定ではこの読み込み先を読まず、SC1091 (info) を出して先へ進む。

読み込み先を読まないので、次の 2 つを誤検知する。

  • 呼び出し側で代入し、読み込み先の関数が読む変数 (greeting) は、使われていない (SC2034) と判定される。bash の関数は、呼び出し元で代入した変数を引数で渡さなくても読める
  • 読み込み先で代入し、呼び出し側で読む変数 (lib_name) は、代入されていない (SC2154) と判定される
main.sh
#!/usr/bin/env bash
source ./lib.sh
greeting=hi
say
echo "$lib_name"
lib.sh
# shellcheck shell=bash
lib_name=lib
say() { echo "$greeting from $lib_name"; }
$ shellcheck main.sh

In main.sh line 2:
source ./lib.sh
       ^------^ SC1091 (info): Not following: ./lib.sh was not specified as input (see shellcheck -x).


In main.sh line 3:
greeting=hi
^------^ SC2034 (warning): greeting appears unused. Verify use (or export if used externally).


In main.sh line 5:
echo "$lib_name"
      ^-------^ SC2154 (warning): lib_name is referenced but not assigned.

$ shellcheck -x main.sh
$ echo $?
0

-x (--external-sources) を付けると読み込み先を読み、3 つとも消える。.shellcheckrc に external-sources=true と書いても同じになる。

source-path=SCRIPTDIR は読み込み先を「どこから探すか」を足す設定で、読むかどうかは変えない。source-path=SCRIPTDIR だけを書いた .shellcheckrc では、3 つの指摘がそのまま残る。

$ cat only-source-path/.shellcheckrc
source-path=SCRIPTDIR
$ cd only-source-path && shellcheck main.sh
(SC1091、SC2034、SC2154 の 3 件。上と同じ)

$ cat with-external/.shellcheckrc
external-sources=true
source-path=SCRIPTDIR
$ cd with-external && shellcheck main.sh
$ echo $?
0

shellcheck main.sh lib.sh と読み込み先も引数に並べると、main.sh の指摘は消える。ただし lib.sh は単体でも検査されるので、lib.sh の greeting に SC2154 が出る。

$ shellcheck main.sh lib.sh

In lib.sh line 3:
say() { echo "$greeting from $lib_name"; }
              ^-------^ SC2154 (warning): greeting is referenced but not assigned.

PITFALL: CI では -x を付けて呼び、エディタの連携や git の hook (commit の前などに走るスクリプト) では付けずに呼ぶと、同じファイルが片方でだけ落ちる。.shellcheckrc に external-sources=true を書けば、呼び方によらず読み込み先を読む。

source= の相対パスは、shellcheck を起動したディレクトリから探される#

読み込むパスが "$(dirname "$0")/lib/m" のように実行時に決まるとき、ShellCheck はその値を知らないので、# shellcheck source=<パス> で読み込み先を教える。$0 は実行したスクリプトのパスで、dirname はその親のディレクトリを返す。source= に書いた相対パスは、検査するスクリプトの場所ではなく、shellcheck を起動したディレクトリ (cwd) から探される。

確かめた構成は次のとおり。

.
├── bin/
│   ├── a        # source=bin/lib/m
│   ├── b        # source-path=SCRIPTDIR source=lib/m
│   ├── c        # directive なし
│   └── lib/m    # lib_name=m を代入する
└── test/
bin/a
#!/bin/sh
# shellcheck source=bin/lib/m
. "$(dirname "$0")/lib/m"
echo "$lib_name"

repo の root から流すと通り、test/ から流すと test/bin/lib/m を探して見つからず、SC1091 と SC2154 になる。

$ shellcheck -x bin/a
$ echo $?
0
$ cd test && shellcheck -x ../bin/a

In ../bin/a line 3:
. "$(dirname "$0")/lib/m"
  ^---------------------^ SC1091 (info): Not following: bin/lib/m: openBinaryFile: does not exist (No such file or directory)


In ../bin/a line 4:
echo "$lib_name"
      ^-------^ SC2154 (warning): lib_name is referenced but not assigned.

同じ directive に source-path=SCRIPTDIR を足し、source= をスクリプトからの相対パスにすると、どこから流しても通る。SCRIPTDIR は検査しているスクリプトのディレクトリ (ここでは bin/) を指す特別な値である。

bin/b
#!/bin/sh
# shellcheck source-path=SCRIPTDIR source=lib/m
. "$(dirname "$0")/lib/m"
echo "$lib_name"
$ shellcheck -x bin/b
$ cd test && shellcheck -x ../bin/b
$ echo $?
0

directive が無い bin/c では、ShellCheck は $(dirname "$0") を . と読み、./lib/m を cwd から探す。bin/ の中から流したときだけ通る。

$ shellcheck -x bin/c

In bin/c line 2:
. "$(dirname "$0")/lib/m"
  ^---------------------^ SC1091 (info): Not following: ./lib/m: openBinaryFile: does not exist (No such file or directory)


In bin/c line 3:
echo "$lib_name"
      ^-------^ SC2154 (warning): lib_name is referenced but not assigned.

$ cd bin && shellcheck -x c
$ echo $?
0

directive を書かずに済ませるなら、.shellcheckrc に 2 行を書く。bin/c と同じ中身のスクリプトを、この .shellcheckrc を置いた rc/ の下に置くと、-x も directive も無しに、別のディレクトリから流しても通る。

$ cat rc/.shellcheckrc
external-sources=true
source-path=SCRIPTDIR
$ cd test && shellcheck ../rc/bin/c
$ echo $?
0

PITFALL: スクリプト自体は実行時の $0 から lib を探すので、sh bin/a も cd test && sh ../bin/a も m を出す。cwd で結果が変わるのは ShellCheck だけなので、repo の root 以外から shellcheck を起動するエディタの連携では、CLI で通るファイルに SC1091 が出る。

disable がファイル全体に効くのは、最初のコマンドより前に置いたときだけ#

# shellcheck disable=SC2034 は、次に来る 1 つのコマンド (関数の定義も 1 つのコマンドとして数える) の指摘を止める。ファイルのどのコマンドよりも前に置いたときだけ、ファイル全体に効く。ShellCheck の wiki (Directive の頁) には “Directives that replace or are immediately after the shebang apply to the entire script. Otherwise, they are scoped to the command that follows it” とある。shebang は 1 行目の #!/usr/bin/env bash のことである。

a.sh は警告なしで通る。

a.sh
#!/usr/bin/env bash
# shellcheck disable=SC2034
x=1
f() { y=2; }
f

b.sh は先頭に関数を 1 つ足しただけだが、directive は次の x=1 にしか効かなくなり、関数 f の中の y=2 に SC2034 が出る。

b.sh
#!/usr/bin/env bash
stub() { :; }
# shellcheck disable=SC2034
x=1
f() { y=2; }
f
$ shellcheck a.sh
$ echo $?
0
$ shellcheck b.sh

In b.sh line 5:
f() { y=2; }
      ^-- SC2034 (warning): y appears unused. Verify use (or export if used externally).

先頭に足すのが「直接実行されたら止める」ガード行でも同じである。ガード行は source 専用のライブラリでよく使う。directive をガード行の下に置くと、y=2 に SC2034 が出る。

guard-below.sh
#!/usr/bin/env bash
[[ "${BASH_SOURCE[0]}" == "${0}" ]] && { echo "source only" >&2; exit 1; }
# shellcheck disable=SC2034
x=1
y=2
$ shellcheck guard-below.sh

In guard-below.sh line 5:
y=2
^-- SC2034 (warning): y appears unused. Verify use (or export if used externally).

境目は shebang の直後かどうかではなく、最初のコマンドより前かどうかである。shebang と directive の間にコメントの行や空行があっても、コマンドが無ければファイル全体に効く。

comment-between.sh
#!/usr/bin/env bash
# source 専用のライブラリ

# shellcheck disable=SC2034
x=1
f() { y=2; }
f
$ shellcheck comment-between.sh
$ echo $?
0

PITFALL: ファイルの先頭に関数やガード行を足す変更で、離れた行に警告が出始める。足すものを directive より後ろに置くか、directive を最初のコマンドより前に戻す。

終了コードは、info の指摘しか無くても 1 になる#

ShellCheck の終了コード 1 は「指摘が 1 件以上ある」の意味で、severity を区別しない。読み込み先を追えない SC1091 (info) だけでも 1 になる。

$ cat main.sh
#!/usr/bin/env bash
source ./lib.sh
say
$ shellcheck main.sh

In main.sh line 2:
source ./lib.sh
       ^------^ SC1091 (info): Not following: ./lib.sh was not specified as input (see shellcheck -x).

$ echo $?
1
$ shellcheck --severity=warning main.sh
$ echo $?
0
$ shellcheck -x main.sh
$ echo $?
0

--severity=warning は warning 以上だけを数える。info を外すと、クォート漏れの SC2086 (info) も外れる (後の節の出力にあるとおり SC2086 は info である)。

PITFALL: CI では -x か --severity=warning を付けて呼んでいると、CI は通るのに手元の素の shellcheck は失敗する。手元の結果を判断する前に、CI の呼び方を確かめる。

代入がすべて安全なリテラルの変数には、SC2086 を出さない#

SC2086 は、クォートしていない変数の展開 ($s) への指摘である。クォートしない展開では、値が空白で分割され (単語分割)、* などの文字がファイル名に展開される (グロブ)。ShellCheck はファイルの中の代入を追い、その変数に入る値がすべて空白もグロブの文字も含まないリテラルなら、SC2086 を出さない。

1-literal.sh
#!/usr/bin/env bash
a() {
  local s=
  [[ $EUID -ne 0 ]] && s=sudo
  env $s id
}
a
3-arg.sh
#!/usr/bin/env bash
b() {
  local s=$1
  env $s id
}
b sudo
$ shellcheck 1-literal.sh
$ echo $?
0
$ shellcheck 3-arg.sh

In 3-arg.sh line 4:
  env $s id
      ^-- SC2086 (info): Double quote to prevent globbing and word splitting.

Did you mean:
  env "$s" id

代入のされ方ごとの結果は次のとおり。ファイルごとに 1 通りずつ書いて流した。

代入のされ方env $s id に SC2086
local s= と s=sudo だけ出ない
呼び出し元の関数で上と同じ代入をし、呼ばれた関数で展開する出ない
local s=$1出る
s="$(command -v sudo)"出る
ファイルの中のどこにも代入が無い出る (SC2154 も出る)

コマンド名の位置 ($s id) では、local s=$1 でも SC2086 は出なかった。

これは意図した動作で、ShellCheck の man page には .shellcheckrc の例として “Turn on warnings for unquoted variables with safe values” と enable=quote-safe-variables が載っている。有効にすると、リテラルだけの変数にも SC2248 (style) が出る。

$ shellcheck --enable=quote-safe-variables 1-literal.sh

In 1-literal.sh line 5:
  env $s id
      ^-- SC2248 (style): Prefer double quoting even when variables don't contain special characters.

Did you mean:
  env "$s" id

PITFALL: 値を引数で渡すように関数を切り出すと、挙動は同じでも SC2086 が出始める。空のときに引数から消すために、わざとクォートしていない変数を "$s" に直すと、空文字の引数が 1 つ渡って壊れる。

$ s=; env $s echo ok; echo "unquoted rc=$?"; env "$s" echo ok; echo "quoted rc=$?"
ok
unquoted rc=0
env: '': No such file or directory
quoted rc=127

空のときに消したい値は配列にする。"${a[@]}" は空の配列なら引数を 1 つも作らず、SC2086 も出ない。count は引数の数を出すだけの関数である。

$ count() { echo "argc=$#"; }; s=; a=(); count $s id; count "$s" id; count "${a[@]}" id
argc=1
argc=2
argc=1
7-array.sh
#!/usr/bin/env bash
f() {
  local sudo=()
  [[ $EUID -ne 0 ]] && sudo=(sudo)
  env "${sudo[@]}" echo ok
}
f
$ shellcheck 7-array.sh
$ echo $?
0

定義の無い関数の呼び出しは指摘されず、実行して初めて 127 になる#

ShellCheck は、定義が見つからない名前を外部コマンド (PATH から探して実行するプログラム) とみなす。実行するときに PATH にあるかは、静的には決められないので指摘しない。改名で消えた関数を呼んでも lint は通り、実行して初めて終了コード 127 (command not found) になる。

log.sh
# shellcheck shell=bash
# log_msg から改名した
log_info() { echo "[info] $*"; }
deploy.sh
#!/usr/bin/env bash
# shellcheck source=./log.sh
source ./log.sh
log_info "start"
log_msg "done" # 改名前の名前のまま残った呼び出し
$ shellcheck -x deploy.sh
$ echo $?
0
$ bash deploy.sh
[info] start
deploy.sh: line 5: log_msg: command not found
$ echo $?
127

共通の関数を改名するブランチと、旧名の呼び出しを足すブランチを別々にマージすると、この形になる。git merge は変更した行が重ならなければ競合なしで両方を取り込むので、マージの後のファイルに旧名の呼び出しが残る。マージと lint だけでは防げないので、マージの後にその呼び出しを通るテストを流す。

SC2329 は、サブシェルの中で定義して呼び出しが見えない関数に出る#

SC2329 (info) は「この関数はどこからも呼ばれていない」という指摘である。0.11.0 で試すと、出るのはサブシェルの中で定義した関数だけで、トップレベルで定義した関数と、{ } の関数の中で定義した関数には、呼ばれていなくても出なかった。サブシェルは ( ... ) で作る子のシェルで、中で定義した関数も代入した変数も、サブシェルを出ると消える。

probe.sh
#!/usr/bin/env bash
# SC2329 がどの関数に出るかの下調べ
top_unused() { echo top; }
outer() {
  inner_unused() { echo inner; }
  echo outer
}
outer
(
  in_subshell_unused() { echo sub; }
  echo sub
)
sub_body() (
  in_sub_body_unused() { echo sub_body; }
  echo sub_body
)
sub_body
$ shellcheck probe.sh

In probe.sh line 10:
  in_subshell_unused() { echo sub; }
  ^-- SC2329 (info): This function is never invoked. Check usage (or ignored if invoked indirectly).


In probe.sh line 14:
  in_sub_body_unused() { echo sub_body; }
  ^-- SC2329 (info): This function is never invoked. Check usage (or ignored if invoked indirectly).

sub_body() ( ... ) のように、関数の本体を { } でなく ( ) で書くと、その関数は呼ばれるたびにサブシェルで走る。テストを関数ごとにこの形で隔離し、その中で差し替えの関数 (stub。テストのために同じ名前で定義し直した関数) を定義すると、SC2329 に当たる。

pick.sh
#!/usr/bin/env bash
draw_candidate() { shuf -n1 -e a b c; }
main() { echo "picked: $(draw_candidate)"; }
[[ "${BASH_SOURCE[0]}" == "${0}" ]] && main
test-pick.sh
#!/usr/bin/env bash
# shellcheck source=./pick.sh
source ./pick.sh

# テストごとにサブシェルで隔離する (差し替えが他のテストに漏れない)
test_main_prints_candidate() (
  draw_candidate() { echo "fixed"; }
  [[ "$(main)" == "picked: fixed" ]]
)

test_main_prints_candidate && echo PASS
$ shellcheck test-pick.sh

In test-pick.sh line 3:
source ./pick.sh
       ^-------^ SC1091 (info): Not following: ./pick.sh was not specified as input (see shellcheck -x).


In test-pick.sh line 7:
  draw_candidate() { echo "fixed"; }
  ^-- SC2329 (info): This function is never invoked. Check usage (or ignored if invoked indirectly).

$ shellcheck -x test-pick.sh
$ echo $?
0
$ bash test-pick.sh
PASS

-x で読み込み先を読むと、main の中の draw_candidate の呼び出しが見えるので消える。呼び出しが見えない形、例えば関数の名前を変数に入れて "$picker" で呼ぶ形では、-x を付けても消えない。

test-indirect.sh
#!/usr/bin/env bash
# 名前を変数に入れて呼ぶ (間接呼び出し)
picker=draw_candidate
main() { echo "picked: $("$picker")"; }

test_main_prints_candidate() (
  draw_candidate() { echo "fixed"; }
  [[ "$(main)" == "picked: fixed" ]]
)

test_main_prints_candidate && echo PASS
$ shellcheck -x test-indirect.sh

In test-indirect.sh line 7:
  draw_candidate() { echo "fixed"; }
  ^-- SC2329 (info): This function is never invoked. Check usage (or ignored if invoked indirectly).

止めるときは、directive を関数の定義の直前の行に置き、どこから呼ばれるかを書く。関数の本体の中 (定義の後ろ) に置いても消えない。下の test_above は消え、test_inside は消えない。

disable-placement.sh
#!/usr/bin/env bash
picker=draw_candidate
main() { echo "picked: $("$picker")"; }

  # shellcheck disable=SC2329 # main から $picker 経由で呼ばれる差し替え
  draw_candidate() { echo "fixed"; }
  [[ "$(main)" == "picked: fixed" ]]
)

test_inside() (
  draw_candidate() {
    # shellcheck disable=SC2329
    echo "fixed"
  }
  [[ "$(main)" == "picked: fixed" ]]
)

test_above && test_inside && echo PASS
$ shellcheck disable-placement.sh

In disable-placement.sh line 12:
  draw_candidate() {
  ^-- SC2329 (info): This function is never invoked. Check usage (or ignored if invoked indirectly).

PITFALL: SC2329 は info なので、--severity=warning で呼ぶ CI では出ず、info も数える hook でだけ止まる。

本体を ( ) で書いた関数で変数を書き換えると、SC2030 と SC2031 が出る#

本体を ( ) で書いた関数の中で変数を書き換えても、書き換えはサブシェルを出ると消え、呼び出し元の値は変わらない。テストを隔離するにはこれが目的どおりの動きだが、ShellCheck は書き換えに SC2030 (書き換えはサブシェルの中だけ) を、同じ変数を別の場所で読む箇所に SC2031 (サブシェルでの書き換えは失われうる) を出す。どちらも info である。

test.sh
#!/usr/bin/env bash
mode=prod

# テストごとにサブシェルで隔離する (mode の書き換えが次のテストに漏れない)
test_dry_run() (
  mode=dry
  [[ $mode == dry ]]
)

test_default_mode() (
  [[ $mode == prod ]]
)

test_dry_run && test_default_mode && echo PASS
$ shellcheck test.sh

In test.sh line 6:
  mode=dry
  ^--^ SC2030 (info): Modification of mode is local (to subshell caused by (..) group).


In test.sh line 10:
test_default_mode() (
                    ^-- SC2235 (style): Use { ..; } instead of (..) to avoid subshell overhead.


In test.sh line 11:
  [[ $mode == prod ]]
     ^---^ SC2031 (info): mode was modified in a subshell. That change might be lost.

$ bash test.sh
PASS

SC2235 (style) は、何も書き換えない関数を ( ) で書いたことへの「{ } にすればサブシェルを作らずに済む」という指摘である。

隔離が目的なら、ファイル全体で止め、理由をコメントに書く。directive は最初のコマンド (mode=prod) より前に置く (前の節)。

test-disabled.sh (先頭の 4 行)
#!/usr/bin/env bash
# テストは関数ごとにサブシェルで隔離する。書き換えが外に出ないのは意図どおり
# shellcheck disable=SC2030,SC2031,SC2235
mode=prod
$ shellcheck test-disabled.sh
$ echo $?
0

PITFALL: ファイル全体で止めると、同じファイルの中の、隔離のつもりでない書き換えにも SC2030 と SC2031 が出なくなる。

正しい構文でも止まる: 引数の done と、$( の直後の ((#

引数の位置に素のまま書いた done は SC1010 になる#

done は for や while のループを閉じる予約語 (シェルが文法の一部として扱う語) である。ShellCheck は、コマンドの引数に素のまま書いた done を、; や改行を書き忘れたループの終わりとみなして SC1010 (warning) を出す。bash は引数の位置の done をただの文字列として渡すので、実行では問題が無い。do、then、fi、esac も同じである。

done-arg.sh
#!/usr/bin/env bash
todo() { echo "todo: $*"; }
todo done 3
TZ=UTC todo done 3
$ shellcheck done-arg.sh

In done-arg.sh line 3:
todo done 3
     ^-- SC1010 (warning): Use semicolon or linefeed before 'done' (or quote to make it literal).


In done-arg.sh line 4:
TZ=UTC todo done 3
            ^-- SC1010 (warning): Use semicolon or linefeed before 'done' (or quote to make it literal).

$ bash done-arg.sh
todo: done 3
todo: done 3

todo "done" 3 と引用すると消える。

PITFALL: 実行では何も起きないので、done や then をサブコマンドに持つ CLI を呼ぶスクリプトは、ShellCheck にだけ止められる。

$( の直後に (( を続けると SC1102 になる#

$( ... ) はコマンド置換 (コマンドの出力を文字列として受け取る)、$(( ... )) は算術展開 (計算した値を受け取る)、(( ... )) は算術の条件 (真なら終了コード 0) である。コマンド置換の先頭に算術の条件を書くと $((( となり、算術展開の始まりとも読めるので、ShellCheck は SC1102 (error) を出す。bash は正しく読む。

arith.sh
#!/usr/bin/env bash
elapsed=700
ok="$(((elapsed >= 500)) && echo yes || echo no)"
echo "$ok"
$ shellcheck arith.sh

In arith.sh line 3:
ok="$(((elapsed >= 500)) && echo yes || echo no)"
    ^-- SC1102 (error): Shells disambiguate $(( differently or not at all. For $(command substitution), add space after $( . For $((arithmetics)), fix parsing errors.

$ bash arith.sh
yes

$( と (( の間に空白を入れると通る。

ok="$( ((elapsed >= 500)) && echo yes || echo no)"

zsh のファイルは解析しない#

ShellCheck が扱うのは sh、bash、dash、ksh、busybox sh で、shebang が zsh のファイルは SC1071 (error) を出して解析をやめる。

ok.zsh
#!/usr/bin/env zsh
files=(*(.))
lines=(${(f)"$(print -l a b)"})
(( $+commands[git] )) && print "git: yes"
print "files=${#files} lines=${#lines}"
$ shellcheck ok.zsh

In ok.zsh line 1:
#!/usr/bin/env zsh
^-- SC1071 (error): ShellCheck only supports sh/bash/dash/ksh/'busybox sh' scripts. Sorry!

zsh のファイルの構文は zsh -n で確かめる。-n はファイルを読むだけで、コマンドを実行しない。

$ zsh -n ok.zsh
$ echo $?
0
$ cat broken.zsh
#!/usr/bin/env zsh
if (( $+commands[git] )); then
  print "git: yes"
$ zsh -n broken.zsh
broken.zsh:4: parse error near `\n'

シェルスクリプトの整形ツール shfmt は、v3.14.1 では方言に zsh を持つ (-ln zsh)。既定の auto のまま流すと、ok.zsh を zsh として読んで整形した。

$ shfmt --help 2>&1 | grep -- --language-dialect
  -ln, --language-dialect str  bash/posix/mksh/bats/zsh, default "auto"
$ shfmt -d ok.zsh
diff ok.zsh.orig ok.zsh
--- ok.zsh.orig
+++ ok.zsh
@@ -1,5 +1,5 @@
 #!/usr/bin/env zsh
 files=(*(.))
 lines=(${(f)"$(print -l a b)"})
-(( $+commands[git] )) && print "git: yes"
+(($+commands[git])) && print "git: yes"
 print "files=${#files} lines=${#lines}"

ただし zsh の構文をすべて読めるわけではない。次の more.zsh では、5 行目の for の短縮形 for f (*.zsh) print $f が parse error になった。5 行目を除いたファイルは shfmt -d が終了コード 0 で通ったので、=(...)、${(j:,:)arr}、repeat、${^arr} は読めている。parse error のとき、shfmt -w (整形結果でファイルを上書きする) はファイルを書き換えずに終了コード 1 で終わる。

more.zsh
#!/usr/bin/env zsh
diff =(print a) =(print b)
arr=(x y z)
print ${(j:,:)arr}
for f (*.zsh) print $f
repeat 2 print hi
[[ $f == (a|b).zsh ]] && print match
print -l ${^arr}.txt
$ shfmt -d more.zsh
more.zsh:5:1: `for foo` must be followed by `in`, `do`, `;`, or a newline
$ cp more.zsh w.zsh; shfmt -w w.zsh; echo "shfmt rc=$?"; cmp more.zsh w.zsh && echo unchanged
w.zsh:5:1: `for foo` must be followed by `in`, `do`, `;`, or a newline
shfmt rc=1
unchanged
$ zsh -n more.zsh
$ echo $?
0

PITFALL: sh 向けの lint をそのまま zsh のファイルにも流すと、ShellCheck は SC1071 の error で毎回落ち、shfmt は zsh の短縮形の構文を含むファイルで落ちる。zsh のファイルは shebang や拡張子で ShellCheck の対象から外し、zsh -n に回す。

actionlint は composite action の run: を ShellCheck に渡さない#

GitHub Actions の workflow (.github/workflows/ に置く YAML) は job の並びで、job は step を上から順に実行する。step は job の中の 1 つの処理で、run: にシェルのコマンドを書くか、uses: で action を呼ぶかのどちらかである。action は、step から uses: で呼び出す再利用できる処理の部品で、action.yaml に入力と中身を定義する。actionlint は workflow の linter で、step の run: に書いたシェルを ShellCheck に掛ける。composite action は、中身を run: などの step の並びで書いた action で、.github/actions/<名前>/action.yaml に置き、workflow から uses: ./.github/actions/<名前> で呼ぶ。actionlint はこの run: を検査しない。actionlint の README は、自身を workflow のファイル用の linter としている。composite action の検査は、2021 年に機能要望 (rhysd/actionlint#46) として出されている。

.github/workflows/ci.yaml
name: ci
on: push
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: echo "x=1" >> $GITHUB_ENV
      - uses: ./.github/actions/a
      - uses: ./.github/actions/b
.github/actions/a/action.yaml
name: a
description: run に書いたシェルを actionlint が検査するか
runs:
  using: composite
  steps:
    - run: echo "x=1" >> $GITHUB_ENV
      shell: bash

$GITHUB_ENV は、後の step に渡す環境変数を書き込むファイルのパスである。同じ echo "x=1" >> $GITHUB_ENV が、workflow では SC2086 になり、action.yaml では何も言われない。引数なしの actionlint は、cwd から上へ辿った git リポジトリの root を project とみなし、その .github/workflows/ の YAML だけを集める。

$ actionlint
.github/workflows/ci.yaml:8:9: shellcheck reported issue in this script: SC2086:info:1:15: Double quote to prevent globbing and word splitting [shellcheck]
  |
8 |       - run: echo "x=1" >> $GITHUB_ENV
  |         ^~~~
$ actionlint -verbose 2>&1 | grep -E "Collected|Linting \."
verbose: Collected 1 YAML files
verbose: Linting .github/workflows/ci.yaml

action.yaml を引数で渡すと、workflow として読んで、workflow に要るキーが無いと指摘する。Vim の lint プラグイン ALE のように、.github/ の下の YAML をすべて actionlint に渡すエディタの連携では、この指摘が action.yaml に出る。

$ actionlint .github/actions/a/action.yaml

composite action のシェルは、run: の中身をスクリプトのファイルに出し、shellcheck で直接検査する。$GITHUB_ACTION_PATH は、実行中の action のディレクトリを指す環境変数である。

.github/actions/b/action.yaml
name: b
description: run の中身を script に出した composite action
runs:
  using: composite
  steps:
    - run: '"$GITHUB_ACTION_PATH/scripts/set-env.sh"'
      shell: bash
$ cat .github/actions/b/scripts/set-env.sh
#!/usr/bin/env bash
echo "x=1" >> $GITHUB_ENV
$ shellcheck .github/actions/*/scripts/*.sh

In .github/actions/b/scripts/set-env.sh line 2:
echo "x=1" >> $GITHUB_ENV
              ^---------^ SC2086 (info): Double quote to prevent globbing and word splitting.

Did you mean:
echo "x=1" >> "$GITHUB_ENV"

PITFALL: actionlint が通っても、composite action の中のクォート漏れは残る。lint の対象に .github/actions/*/scripts/*.sh を足さない限り、どの lint にも掛からない。
