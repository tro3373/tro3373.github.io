direnv の環境が入る経路と exit 0 で通る失敗

2026-11-27 ·  2026-11-27 · 9 分 · 1844 文字

結論#

  • direnv が .envrc の値を入れるのは、フックを入れた対話シェルと、direnv exec で起動したコマンドだけ。direnv を読み込んでいないシェルやプロセスから、tmux の pane・cron・bash -c のようにプロンプトを出さずに起動したコマンドには、cd しても入らない
  • 読む .envrc は、ディレクトリから上へ探して最初に見つかった 1 つだけ。親の値は、子の .envrc に source_up_if_exists を書いて読む。こうして読まれた親は、許可を確かめられない
  • .envrc の中の失敗は終了コードに出ない。未定義の use、nix が PATH に無い use flake、失敗するコマンドの行は、エラーを出すだけで後ろの行を評価し、direnv exec は後ろのコマンドを走らせて 0 を返す。1 で止まったのは、未許可の .envrc、存在しないディレクトリ、.envrc が exit で抜けたとき。止めたい行には || exit 1 を付ける
  • direnv を読み込んだシェルの子が .envrc の外でフックを走らせると、unload (読み込みの取り消し) が変数を読み込み前の値に戻す。読み込みの後に足した PATH の要素も消える

以下は direnv 2.38.2 / zsh 5.9.2 / GNU bash 5.3.20 / Linux x86_64 で確かめた。 コードは、どれも次の 2 行で作った一時ディレクトリで、上から順に実行した。 XDG_CONFIG_HOME と XDG_DATA_HOME を一時ディレクトリに向けて、手元の direnv の設定と許可の記録を使わないようにしている (既定はそれぞれ ~/.config と ~/.local/share)。 出力に出る一時ディレクトリのパスは <tmp> と書く。

cd "$(mktemp -d)"
export XDG_CONFIG_HOME=$PWD/config XDG_DATA_HOME=$PWD/data

前提: direnv が環境を入れる 2 つの経路#

direnv は、ディレクトリごとに環境変数を切り替えるツール。 ディレクトリに置いた .envrc に export FOO=1 のような行を書くと、そのディレクトリの下で作業する間だけ FOO が入る。

  • .envrc は bash のスクリプトとして評価される
    • 評価の前に、direnv の組み込み関数群 (stdlib) と、利用者の設定ファイル ~/.config/direnv/direnvrc が読み込まれる
    • stdlib には PATH_add (PATH の先頭にディレクトリを足す)、source_up、use などがある。中身は direnv stdlib で表示できる
  • 新しい .envrc と書き換えた .envrc は、direnv allow <ディレクトリ> で許可するまで評価されない。許可が無いと is blocked のエラーになる

環境を入れる経路は 2 つある。

  1. フック: .zshrc に eval "$(direnv hook zsh)" を書くと、zsh がプロンプトを出す直前と cd の後に _direnv_hook 関数を呼ぶ。_direnv_hook は direnv export zsh を実行し、出てきた export / unset の文を今のシェルで評価する。direnv export <シェル> は、今のディレクトリに合わせて環境を変える文を出すコマンド
  2. direnv exec <DIR> <コマンド>: 呼ぶたびに DIR の .envrc を評価し、その環境でコマンドを起動する

どちらも通らないプロセスには、.envrc の値は入らない。

対話シェルにはプロンプトのたびに入る#

direnv hook zsh が出すコードは、_direnv_hook を zsh の 2 つの配列に登録する。

  • precmd_functions: zsh がプロンプトを出す直前に呼ぶ関数の並び
  • chpwd_functions: zsh が cd でディレクトリを変えた後に呼ぶ関数の並び

_direnv_hook 自身は、対話シェルでない (-o interactive でない) ときとサブシェルの中では何もせずに戻る。

direnv hook zsh | grep -nE 'interactive|export zsh|chpwd_functions|precmd_functions'
4:  if [[ ! -o interactive || $ZSH_SUBSHELL -ne 0 ]]; then
7:  vars="$($'/usr/bin/direnv' export zsh)"
12:typeset -ag precmd_functions
13:if (( ! ${precmd_functions[(I)_direnv_hook]} )); then
14:  precmd_functions=(_direnv_hook $precmd_functions)
16:typeset -ag chpwd_functions
17:if (( ! ${chpwd_functions[(I)_direnv_hook]} )); then
18:  chpwd_functions=(_direnv_hook $chpwd_functions)

precmd にも入っているので、cd しなくても、.envrc を書き換えて許可し直せば次のプロンプトの前に読み直される。 対話の zsh に標準入力から 1 行ずつ流して確かめる。-f で .zshrc を読まず、-i で対話シェルにし、PS1= でプロンプトを空に、-o nopromptsp で行末の % を消す。

mkdir h && echo 'export FOO=1' > h/.envrc && direnv allow h
printf '%s\n' \
  'eval "$(direnv hook zsh)"' \
  'cd h' \
  'echo "FOO=$FOO"' \
  'sleep 1; echo "export FOO=2" > .envrc; direnv allow .' \
  'echo "FOO=$FOO"' \
  | PS1= zsh -fi -o nopromptsp 2>&1
direnv: loading <tmp>/h/.envrc
direnv: export +FOO
FOO=1
direnv: loading <tmp>/h/.envrc
direnv: export +FOO
FOO=2

direnv: loading は評価した .envrc、direnv: export +FOO は足した変数を示す direnv のログで、stderr に出る。

direnv は前回の状態を、読み込んだシェルの環境変数 DIRENV_DIFF と DIRENV_WATCHES に持つ。 DIRENV_WATCHES には、見張るファイル (.envrc と許可の記録) のパスと mtime (更新時刻) が秒の単位で入る (direnv show_dump "$DIRENV_WATCHES" で読める)。 上で sleep 1 を挟んでいるのはこのため。読み込みと同じ秒の中で書き換えると、次のプロンプトでは読み直されなかった。秒が進んでから touch .envrc で mtime を変えると読み直された。

  • PITFALL: 読み直されるのはシェルの環境だけ。すでに動いているプロセス (エディタ、AI のコーディングエージェントのセッションなど) の環境は変わらない。.envrc を変えたら、それらは起動し直す

プロンプトを出さない子プロセスには入らない#

.envrc の値は、フックが走ったシェルにしか無い。 読み込み済みの対話シェルから起動した子プロセスは、export された値を引き継ぐので値を持つ。 値が無いのは、direnv を読み込んでいないシェルやプロセス (cron、tmux サーバ、エディタなど) から起動した子プロセス。 プロンプトを出さない子プロセス (bash -c、スクリプト、cron のジョブ) はフックを走らせないので、.envrc のあるディレクトリへ cd しても値が入らない。 direnv exec で起動すると、その場で .envrc を評価してから走る。 下の例は、direnv を読み込んでいない (FOO を持たない) シェルから打っている。

mkdir np && echo 'export FOO=from-envrc' > np/.envrc && direnv allow np
printf '#!/bin/sh\necho "FOO=$FOO"\n' > np/run.sh
bash -c 'cd np && sh run.sh'
(cd np && direnv exec . sh run.sh)
FOO=
direnv: loading <tmp>/np/.envrc
FOO=from-envrc

tmux の pane も同じ。split-window にコマンドを渡すと、そのコマンドはプロンプトを出さないまま走る。 しかも pane のプロセスを起動するのは split-window を打ったシェルでなく tmux サーバで、pane の環境は、tmux サーバが持つ環境変数の表 (全体用の global と、セッションごとの表) から作られる ( tmux サーバが握り続ける状態とエラーなしに通るコマンド )。 direnv を読み込んだシェルから打っても、その値は pane に渡らない。direnv exec . を前に付けると、pane の中で .envrc を評価する。

tmux split-window -h -c "$PWD" "direnv exec . bash run.sh"

tmux の行は手元の検証環境で tmux サーバに繋げず、確かめていない。

  • PITFALL: 欠けるのは値だけではない。PATH を差し替える .envrc (後述の use flake など) だと、.envrc が用意した版でなく、システムに入っている版の terraform や gcloud が使われうる
  • PITFALL: direnv exec は呼ぶたびに .envrc を評価する。use flake なら、キャッシュがあっても数秒かかる

direnv exec は第 1 引数のファイルから .envrc を探す#

direnv help の書式は exec DIR COMMAND [...ARGS] だが、第 1 引数がファイルなら、それがコマンドになり、残りは引数になる。 .envrc は第 1 引数のディレクトリ (ファイルならその親) から上へ探す。 cron の行のように、DIR とスクリプトのパスを 2 度書きたくない場面で短く書ける。

mkdir -p repo/scripts && echo 'export FOO=from-root-envrc' > repo/.envrc && direnv allow repo
printf '#!/bin/sh\necho "FOO=$FOO PWD=$PWD args=$*"\n' > repo/scripts/start.sh
chmod +x repo/scripts/start.sh
direnv exec repo/scripts/start.sh a b
direnv exec repo repo/scripts/start.sh a b
direnv: loading <tmp>/repo/.envrc
FOO=from-root-envrc PWD=<tmp> args=a b
direnv: loading <tmp>/repo/.envrc
FOO=from-root-envrc PWD=<tmp> args=a b

PWD は呼び出し元の <tmp> のまま。direnv は環境を被せるだけで、cwd は変えない。 スクリプトの置き場からの相対パスで読むスクリプトは、スクリプトの中で自分で cd しないと失敗する。

printf '#!/bin/sh\ncat ./data.txt\n' > repo/scripts/read.sh && chmod +x repo/scripts/read.sh
echo in-scripts > repo/scripts/data.txt
direnv exec repo/scripts/read.sh
direnv: loading <tmp>/repo/.envrc
cat: ./data.txt: No such file or directory

direnv help は「最初に見つかった .envrc か .env を読む」と書くが、.env (KEY=value を並べるファイル) を探すのは、設定ファイル direnv.toml で load_dotenv = true にしたときだけだった。 有効にすると、近い方の .env で探索が止まり、上の .envrc は読まれない。

echo 'FOO=from-dotenv' > repo/scripts/.env
direnv exec repo/scripts/start.sh    # 既定では .env を飛ばし、repo/.envrc を読む
mkdir -p "$XDG_CONFIG_HOME/direnv"
printf '[global]\nload_dotenv = true\n' > "$XDG_CONFIG_HOME/direnv/direnv.toml"
direnv allow repo/scripts
direnv exec repo/scripts/start.sh    # 近い方の .env で止まる
rm "$XDG_CONFIG_HOME/direnv/direnv.toml" repo/scripts/.env
direnv: loading <tmp>/repo/.envrc
FOO=from-root-envrc PWD=<tmp> args=
FOO=from-dotenv PWD=<tmp> args=

読むのは一番近い .envrc 1 つだけ#

direnv は、ディレクトリから上へ探して最初に見つかった .envrc だけを評価する。 子のディレクトリに .envrc があると、親の .envrc で export した値は入らない。

mkdir -p parent/child
echo 'export A=parent' > parent/.envrc
echo 'export B=child' > parent/child/.envrc
direnv allow parent && direnv allow parent/child
direnv exec parent/child sh -c 'echo "A=$A B=$B"'
direnv: loading <tmp>/parent/child/.envrc
A= B=child

親の値を引き継ぐには、stdlib の関数で明示する。 子の .envrc の先頭に source_up_if_exists を書くと、上のディレクトリの .envrc を探して先に評価する。同じ変数は、後に書いた子の行が上書きする。

printf '%s\n' 'source_up_if_exists' 'export A=child-override B=child' > parent/child/.envrc
direnv allow parent/child
direnv exec parent/child sh -c 'echo "A=$A B=$B"'
direnv: loading <tmp>/parent/child/.envrc
direnv: loading <tmp>/parent/.envrc
A=child-override B=child

source_up も同じく親を読むが、親が見つからないと No ancestor .envrc found を出す。source_up_if_exists は何も出さない。 source_up のメッセージはエラーに見えるが、後ろの行の評価は続き、終了コードも 0 だった (後の節「.envrc の失敗は終了コードに出ない」と同じ扱い)。

mkdir solo
printf '%s\n' 'source_up' 'export Z=after' > solo/.envrc && direnv allow solo
direnv exec solo sh -c 'echo "Z=$Z"'; echo "rc=$?"
direnv: loading <tmp>/solo/.envrc
direnv: No ancestor .envrc found
Z=after
rc=0
  • PITFALL: 親の値はすべて入る。親にトークンを置いていれば、子のディレクトリでも使われる
  • PITFALL: source_up / source_up_if_exists が読む親の .envrc は、許可を確かめられない。stdlib の source_up のコメントにも NOTE: the other ".envrc" is not checked by the security framework. と書かれている。親を書き換えて未許可にしても、子からは読まれる
echo 'export A=parent-edited' > parent/.envrc   # 書き換えたので、parent の許可は外れる
direnv exec parent sh -c 'echo "A=$A"'
printf '%s\n' 'source_up_if_exists' 'export B=child' > parent/child/.envrc && direnv allow parent/child
direnv exec parent/child sh -c 'echo "A=$A B=$B"'
direnv: error <tmp>/parent/.envrc is blocked. Run `direnv allow` to approve its content
direnv: loading <tmp>/parent/child/.envrc
direnv: loading <tmp>/parent/.envrc
A=parent-edited B=child

許可が .envrc のどのパスに付くかは git worktree で共有されるものと分かれるもの に書いた。

use <name> は use_<name> を呼ぶだけ#

stdlib の use は、第 1 引数から関数名 use_<name> を組み立て、残りの引数を渡して呼ぶ。呼ぶ前に using <引数> をログに出す。

direnv stdlib | sed -n '/^use() {/,/^}/p'
use() {
  local cmd=$1
  log_status "using $*"
  shift
  "use_$cmd" "$@"
}

~/.config/direnv/direnvrc と ~/.config/direnv/lib/*.sh は .envrc より先に読み込まれる。 そこに use_<name> を定義すれば、どの .envrc からも use <name> で呼べる。 複数のディレクトリの .envrc で同じ読み込み処理を使い回すときに使う。

mkdir -p "$XDG_CONFIG_HOME/direnv"
cat > "$XDG_CONFIG_HOME/direnv/direnvrc" <<'EOF'
use_hello() {
  export GREETING="hello ${1:-world}"
}
EOF
mkdir u && echo 'use hello direnv' > u/.envrc && direnv allow u
direnv exec u sh -c 'echo "GREETING=$GREETING"'
direnv: loading <tmp>/u/.envrc
direnv: using hello direnv
GREETING=hello direnv

.envrc に use_hello direnv と直接書いても同じ値が入る。違いは using のログが出ないことだけ。 暗号化した dotenv を復号して読み込む use_sops を direnvrc に定義する例は、 sops の暗号文・鍵・平文はどこに残るか に書いた。

  • PITFALL: direnvrc に書いた関数は、そのマシンの direnv にしか無い。.envrc をコミットして他の人が使うなら、同じ関数が要る。無いときにどうなるかは次の節

.envrc の失敗は終了コードに出ない#

.envrc は bash で評価されるが、errexit (set -e。失敗したコマンドでスクリプトを止める設定) は掛かっていない ( bash の set -e が効かない場所と効きすぎる場所 )。 失敗したコマンドの行はその行だけ失敗し、評価は次の行へ進む。 direnv exec は評価を終えるとコマンドを起動し、.envrc の中の失敗を終了コードに出さない。 最後の行が失敗しても、終了コードは 0 だった。

未定義の use#

use sops と書いたが、use_sops を定義した direnvrc が無い場合。use_sops は stdlib に無い。

mkdir undef && printf '%s\n' 'export A=1' 'use sops' 'export B=2' > undef/.envrc && direnv allow undef
direnv exec undef sh -c 'echo "A=$A B=$B"'; echo "rc=$?"
direnv: loading <tmp>/undef/.envrc
direnv: using sops
/usr/bin/bash:1222: use_sops: command not found
A=1 B=2
rc=0
  • PITFALL: use_sops が入れるはずだった変数が欠けたまま進むので、その変数を使う後の工程が落ちるまで気付かない

nix が PATH に無い use flake#

use flake は、Nix (パッケージマネージャ) の flake (リポジトリに置く flake.nix) に書いた devShell (開発用のツールと環境変数の一式) を読み込む stdlib の関数。 中身は、nix ... print-dev-env の出力を eval する。

direnv stdlib | sed -n '/^use_flake() {/,/^}/p' | grep -E 'print-dev-env|eval'
  result="$(nix --extra-experimental-features "nix-command flakes" print-dev-env --profile "$(direnv_layout_dir)/flake-profile" "$@")"
  eval "$result"

nix が PATH に無いと nix: command not found が出て、eval は空の文字列を評価するだけになる。 cron・systemd・CI のように、ログインシェルの初期化 (nix を PATH に足す処理) を通らない環境で起きる。nix の入っていない環境で試す。

command -v nix || echo 'nix: not on PATH'
mkdir flake && echo 'use flake' > flake/.envrc && direnv allow flake
direnv exec flake sh -c 'echo "command ran"'; echo "rc=$?"
nix: not on PATH
direnv: loading <tmp>/flake/.envrc
direnv: using flake
/usr/bin/bash:1444: nix: command not found
touch: setting times of '<tmp>/flake/.direnv/flake-profile': No such file or directory
/usr/bin/bash:1448: nix: command not found
command ran
rc=0

nix をインストールした環境なら、nix を PATH に足すスクリプトを先に読ませてから direnv exec を呼ぶ (この形は nix の無い手元では確かめていない)。

. "$HOME/.nix-profile/etc/profile.d/nix.sh" && \
  direnv exec /path/to/repo /path/to/repo/scripts/start.sh

止まらずに通ったことを検知するなら、devShell が入れるはずの変数 (下の MY_DEVSHELL は、devShell に足しておく自前の変数) を、スクリプトの先頭で確かめる。 下では direnv のログを tail -1 で落とし、スクリプトの最後の行だけを出している。

direnv exec flake bash -c '
  [[ -n ${MY_DEVSHELL:-} ]] || { echo "devShell に入れていない" >&2; exit 1; }
  echo "command ran"
' 2>&1 | tail -1
echo "rc=${PIPESTATUS[0]}"
devShell に入れていない
rc=1
  • PITFALL: 素通りしたまま後続が走ると、ホストに入っている古いツールで動き、別のエラー (「go のバージョンが低い」など) で落ちる。エラーは後続のツールの問題に見えるので、原因が .envrc の読み込みの失敗だと気付きにくい

途中で失敗する行#

false も、存在しないコマンドも、その行だけが失敗する。

mkdir fail
printf '%s\n' 'export A=1' 'false' 'no-such-command' 'export B=2' > fail/.envrc && direnv allow fail
direnv exec fail sh -c 'echo "A=$A B=$B"'; echo "rc=$?"
direnv: loading <tmp>/fail/.envrc
./.envrc:3: no-such-command: command not found
A=1 B=2
rc=0

構文エラーの行は、そこから後ろが評価されない。それでも終了コードは 0 で、コマンドは走る。

mkdir syn
printf '%s\n' 'export A=1' 'if then' 'export B=2' > syn/.envrc && direnv allow syn
direnv exec syn sh -c 'echo "A=$A B=$B"'; echo "rc=$?"
direnv: loading <tmp>/syn/.envrc
./.envrc:2: syntax error near unexpected token `then'
./.envrc:2: `if then'
A=1 B=
rc=0

1 で止まったのは、未許可・存在しないディレクトリ・exit#

未許可の .envrc と存在しないディレクトリは、.envrc を評価する前に止まり、コマンドも起動しない。

mkdir blocked && echo 'export X=1' > blocked/.envrc    # allow しない
direnv exec blocked sh -c 'echo "command ran"'; echo "rc=$?"
direnv exec no-such-dir sh -c 'echo "command ran"'; echo "rc=$?"
direnv: error <tmp>/blocked/.envrc is blocked. Run `direnv allow` to approve its content
rc=1
direnv: error stat no-such-dir: no such file or directory
rc=1

.envrc が exit で抜けたときも、direnv: error exit status 1 を出して 1 で止まり、コマンドは起動しない。 失敗したら止めたい行には || exit 1 を付ける。

mkdir stop
printf '%s\n' 'export A=1' 'use sops || exit 1' 'export B=2' > stop/.envrc && direnv allow stop
direnv exec stop sh -c 'echo "command ran"'; echo "rc=$?"
direnv: loading <tmp>/stop/.envrc
direnv: using sops
/usr/bin/bash:1222: use_sops: command not found

rc=1

対話シェルのフックでも、exit で抜けた .envrc の値は 1 つも入らなかった (export A=1 は exit より前の行だが、A は空のまま)。

.envrc の外で開いた子シェルは PATH を読み込み前の値に戻す#

direnv を読み込んだシェルは、DIRENV_DIR・DIRENV_FILE・DIRENV_DIFF・DIRENV_WATCHES を export している。子プロセスはこれを引き継ぐ。 子が対話シェルなら、.zshrc で入れたフックが最初のプロンプトの前に走る。 そのとき .envrc の外のディレクトリにいると、direnv は「.envrc の外に出た」と判断して direnv: unloading を出し、.envrc が変えた変数を読み込み前の値に戻す。

DIRENV_DIFF には、.envrc が変えた変数の、読み込み前の値と読み込み後の値が入っている。 unload は読み込みで足した分を引くのでなく、変数を読み込み前の値で上書きする。 そのため、読み込みの後に足した PATH の要素も一緒に消える。 たとえば PATH_add bin を書いた repo の中から、テスト用のスクリプトが一時ディレクトリに偽の tool コマンドを作って PATH の先頭に足し、その一時ディレクトリで子シェルを起こして動作を確かめるとする。 子シェルのフックが unload するので、偽の tool は PATH から消え、テストは偽のコマンドを使わずに走る。

下では、PATH を短くして値を並べる。親のシェルでは、フックの代わりに direnv export bash を 1 回評価して読み込む。

mkdir -p withpath/bin other fake
echo 'PATH_add bin' > withpath/.envrc && direnv allow withpath
printf '#!/bin/sh\necho fake-tool\n' > fake/tool && chmod +x fake/tool
(
  w=$PWD; export PATH=/usr/bin:/bin     # direnv が /usr/bin に無いなら、その場所も足す
  echo "before: $PATH"
  cd withpath && eval "$(direnv export bash 2>/dev/null)"   # フックと同じ処理を 1 回
  echo "loaded: $PATH"
  PATH="$w/fake:$PATH" && echo "added:  $PATH"
  cd "$w/other" && bash -c 'eval "$(direnv export bash)"; echo "child:  $PATH"; tool'
)
before: /usr/bin:/bin
loaded: <tmp>/withpath/bin:/usr/bin:/bin
added:  <tmp>/fake:<tmp>/withpath/bin:/usr/bin:/bin
direnv: unloading
child:  /usr/bin:/bin
bash: line 1: tool: command not found

子の PATH は、親が .envrc を読み込む前の /usr/bin:/bin に戻り、後から足した fake も消えた。 子を起こす前に DIRENV_* を消すと、direnv には unload する対象が無くなり、今の PATH が残る。

(
  w=$PWD
  cd withpath && eval "$(direnv export bash 2>/dev/null)"
  PATH="$w/fake:$PATH"
  cd "$w/other"
  for v in $(env | grep -o '^DIRENV_[A-Z_]*'); do unset "$v"; done
  bash -c 'eval "$(direnv export bash)"; tool'
)
fake-tool
  • PITFALL: .envrc が PATH を変えていなければ、direnv: unloading は出ても PATH は消えない。PATH を変える .envrc (PATH_add、use flake など) のときだけ起きるので、再現条件を取り違えやすい
mkdir nopath && echo 'export X=1' > nopath/.envrc && direnv allow nopath
(
  w=$PWD
  cd nopath && eval "$(direnv export bash 2>/dev/null)"
  PATH="$w/fake:$PATH"
  cd "$w/other" && bash -c 'eval "$(direnv export bash)"; tool'
)
direnv: unloading
fake-tool
