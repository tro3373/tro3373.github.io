git の取り込み済み判定は何を比べ、どこで誤るか

2026-11-25 ·  2026-11-25 · 15 分 · 3002 文字

結論#

  • ブランチが取り込み済みかを、1 つのコマンドで言い切る方法は無い。git の判定は、コミットの SHA (base から辿れるか)、patch の中身 (patch-id)、ファイルの中身 (tree) のどれか 1 つだけを比べる。どれも、別の方法で取り込んだブランチを見落とす。base は取り込み先のブランチで、この記事では main
  • git branch --merged・git rev-list --count・git merge-base --is-ancestor・git branch -d は SHA で比べる。squash merge・rebase・cherry-pick で取り込んだブランチを未取り込みと判定し、作っただけでコミットの無いブランチを取り込み済みと判定する。3 つの取り込み方は、どれも元のコミットとは別のコミットを base に作る (違いは 前提 の節)
  • git cherry は patch-id で比べるので、rebase・cherry-pick で取り込んだコミットに - を付ける。2 本以上を 1 本にまとめた squash merge と、取り込むときに競合を手で直したコミットには + を付ける
  • 比べる相手は手元の ref。ref はブランチやタグのように、コミットを指す名前のこと。--merged main の結果は git fetch では変わらない
  • upstream は、ブランチに設定した追跡先のリモートのブランチ (feat なら origin/feat など)。HEAD は、いま checkout しているブランチ (またはコミット)。upstream が消えたブランチを branch -d で消そうとすると、git は HEAD と比べる
  • merge-base --is-ancestor の非 0 には、「祖先でない (1)」と「git のエラー (128)」の 2 つがある
  • 「作っただけ」と「取り込んだ」の区別は reflog にしか残らない。reflog は、ブランチの先頭が作成・commit・reset などで動くたびに、手元の repo に 1 行ずつ書かれる記録。ブランチを消した後は、merge コミットの題名しか残らない

以下はすべて git 2.56.1 で実測した。GIT_CONFIG_GLOBAL=/dev/null で ~/.gitconfig を読ませず、コミットの日時を固定して実行している。

前提: 3 つの比べ方#

コミットの SHA は、tree (その時点の全ファイル)・親・author と committer・日時・メッセージから作るハッシュ。 ブランチを base に取り込む方法ごとに、base に入るコミットが違う。

取り込み方base に入るもの元のコミット
merge (merge コミット)元のコミットと、base とブランチの両方を親に持つ merge コミットbase の履歴に入る
squash mergeブランチの変更をまとめた、新しいコミット 1 本入らない
rebase (rebase merge)ブランチのコミットを 1 本ずつ base の先頭に作り直したコミット。差分は同じで親が違う入らない
cherry-pick指定したコミットの差分を base の上に当てた、新しいコミット入らない

squash merge・rebase・cherry-pick では元のコミットが base の履歴に入らないので、SHA で比べる判定からは、同じ変更が base にあることが見えない。

patch-id は、コミットが入れた差分から作る ID。行番号を無視し、既定では空白も取り除いて計算する (man git-patch-id)。 親が替わっても差分が同じなら同じ値になるので、git cherry はこれで「同じ変更が base にあるか」を判定する。

比べるものコマンド取り込み済みとみなす条件
SHAbranch --merged, rev-list --count, merge-base --is-ancestor, branch -dブランチの先頭のコミットが base から辿れる
patch-idgit cherry, git patch-id同じ差分のコミットが base にある
treegit diff --exit-code2 つのコミットのファイルがすべて同じ

同じ repo で、取り込み方の違う 5 本のブランチを 2 つの方法で判定した結果:

ブランチgit branch --merged maingit cherry main <branch>
merge コミットで取り込んだ出る何も出ない
squash merge した (2 コミットを 1 本に)出ない2 行とも +
cherry-pick で取り込んだ出ない2 行とも -
作っただけ (コミット 0)出る何も出ない
取り込んでいない出ない+

git cherry は、ブランチにあって base から辿れないコミットを 1 行ずつ出す。辿れないコミットが無ければ何も出さない。 squash merge の行はどちらの方法でも「未取り込み」になる。 ブランチのコミットが 1 本だけなら、squash しても差分が同じなので patch-id が一致する ( git rebase の記事 の「squash merge された下段の上に載せる」の節)。

SHA で比べる判定#

作っただけのブランチは取り込み済み、squash merge したブランチは未取り込みになる#

--merged と「rev-list --count main..<branch> が 0」は、どちらもブランチの先頭が base から辿れるかを見る。 作ったばかりのブランチの先頭は base のコミットそのものなので辿れる。squash merge は base に別のコミットを作るので、元のコミットは辿れない。

git init -q -b main demo && cd demo
git commit -q --allow-empty -m init
echo base >> f && git add f && git commit -qm base

git branch never                                  # 作っただけ
git switch -qc work
echo 1 >> w && git add w && git commit -qm "work: 1"
git switch -q main
git merge -q --no-ff --no-edit work               # merge コミットで取り込む

git switch -qc squashed
echo 1 >> s && git add s && git commit -qm "squashed: 1"
echo 2 >> s && git add s && git commit -qm "squashed: 2"
git switch -q main
git merge -q --squash squashed >/dev/null && git commit -qm "squashed (squash merge)"

git switch -qc wip
echo 1 >> x && git add x && git commit -qm "wip: 1"   # まだ取り込んでいない
git switch -q main
$ git branch --merged main
* main
  never
  work
$ git rev-list --count main..never
0
$ git rev-list --count main..squashed
2

git rev-list --left-right --count A...B は、A だけにあるコミットの数と B だけにあるコミットの数をタブ区切りで出す。 ブランチの ahead / behind を一覧に出すときに、git を 1 回起動するだけで両方が取れる。

$ git rev-list --left-right --count main...never
3	0
$ git rev-list --left-right --count main...squashed
1	2
$ git rev-list --left-right --count main...wip
0	1

ahead (右の数) が 0 のブランチは、取り込み済みか、1 度もコミットしていないかのどちらか。コミットグラフにはブランチで作業したかの記録が無いので、区別はブランチの reflog で付ける。

$ git reflog show never
9f74daf never@{0}: branch: Created from main
$ git reflog show work
295947b work@{0}: commit: work: 1
9f74daf work@{1}: branch: Created from HEAD

git branch -m で改名すると reflog は引き継がれ、Branch: renamed ... の行が 1 行増える。行数でなく、commit で始まる行があるかを見る。

$ git branch -m never never2
$ git reflog show --format=%gs never2 | grep -c '^commit'
0
$ git reflog show --format=%gs work | grep -c '^commit'
1
  • PITFALL: reflog は手元にしか無く、clone には引き継がれない。期限 (gc.reflogExpire、既定 90 日) を過ぎた行は消える
  • PITFALL: squash merge と rebase merge は、SHA で比べる判定では拾えない。GitHub などで squash して取り込む repo では、この判定の「未取り込み」は当てにならない

--merged main は手元の main と比べる#

git fetch が進めるのは origin/main だけ。手元の main を進めていなければ、リモートで merge 済みのブランチは --merged main に出ない。 --merged は渡したコミットから辿れるかを見るだけで、リモートとの関係は見ない。

リモートで feat と feat2 を merge し、リモートのブランチを消した後 (PR のマージに当たる)、手元で fetch だけした状態を作る。

d=$(mktemp -d)
git init -q --bare -b main "$d/origin.git"
git clone -q "$d/origin.git" "$d/a" 2>/dev/null && cd "$d/a"
git commit -q --allow-empty -m init && git push -q origin main
for b in feat feat2; do
  git switch -qc $b main
  echo 1 >> $b && git add $b && git commit -qm "$b: 1"
  git push -q -u origin $b
done
git switch -q main
# 別の clone で merge して push し、リモートのブランチを消す
git clone -q "$d/origin.git" "$d/b"
git -C "$d/b" merge -q --no-ff --no-edit origin/feat
git -C "$d/b" merge -q --no-ff --no-edit origin/feat2
git -C "$d/b" push -q origin main
git -C "$d/b" push -q origin --delete feat feat2
$ git fetch -q --prune
$ git branch --merged main
* main
$ git branch --merged origin/main
  feat
  feat2
* main
$ git branch -vv
  feat  1b95c22 [origin/feat: gone] feat: 1
  feat2 40634da [origin/feat2: gone] feat2: 1
* main  3234635 [origin/main: behind 4] init

[origin/feat: gone] は、upstream に設定したリモートのブランチが消えたことを示す。

  • PITFALL: squash merge・rebase merge したブランチは --merged origin/main にも出ない。: gone] で拾えるが、: gone] にはマージせずにリモートだけ消したブランチも混ざる

merge-base --is-ancestor の非 0 は 2 種類ある#

git merge-base --is-ancestor A B は、A が B から辿れれば 0、辿れなければ 1 を返す。A か B が存在しないコミットなら、判定をせずに git のエラーとして 128 を返す。

git merge-base --is-ancestor <A> main の A を替えた結果:

A に渡したもの終了コードstderr
main から辿れるコミット0なし
別の枝のコミット1なし
存在しない SHA128fatal: Not a valid commit name <sha>
ブランチを消して GC したコミット128fatal: Not a valid commit name <sha>

B の側に存在しない SHA を渡しても (git merge-base --is-ancestor main <sha>)、同じ文言で 128 になる。

GC したコミットは、ブランチを git branch -D で消し、git reflog expire --expire=now --expire-unreachable=now --all と git gc --prune=now で消して作った。

if で受けると、128 も else 側に入る。

$ if git merge-base --is-ancestor 0123456789abcdef0123456789abcdef01234567 main 2>/dev/null; then echo on-base; else echo off-base; fi
off-base

$? を 3 つに分けて受ける。

git init -q -b main demo && cd demo
git commit -q --allow-empty -m init
echo 1 >> f && git add f && git commit -qm "main: 1"
git switch -qc side HEAD~1
echo 1 >> g && git add g && git commit -qm "side: 1"
git switch -q main

check() {
  git merge-base --is-ancestor "$1" main 2>/dev/null; rc=$?
  case $rc in 0) echo on-base ;; 1) echo off-base ;; *) echo "error (rc=$rc)" ;; esac
}
$ check main~1
on-base
$ check side
off-base
$ check 0123456789abcdef0123456789abcdef01234567
error (rc=128)
  • PITFALL: 「祖先でない」と「コミットが消えた」をまとめて非 0 で拾う書き方は、両方を同じに扱いたいときにだけ使う。分けたいときは 1 と 128 を別に受ける

消すときに git が確かめること#

upstream が消えると、branch -d は今の HEAD と比べる#

git branch -d は、ブランチが upstream に取り込み済みのときだけ消す。upstream が無ければ HEAD に取り込み済みのときだけ消す。 git fetch --prune で upstream の参照が消えると、比べる相手は削除を実行した時点の HEAD になる。HEAD が main かどうかは見ない。

「--merged main は手元の main と比べる」で作った状態 (fetch だけして、手元の main は古い) から、別の作業ブランチにいながら feat を消す。

git switch -qc other
echo 1 >> o && git add o && git commit -qm "other: 1"
$ git branch -d feat
error: the branch 'feat' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D feat'
hint: Disable this message with "git config set advice.forceDeleteBranch false"

終了コードは 1。main に移って origin/main まで進めた後なら消える。

$ git switch -q main
$ git merge -q --ff-only origin/main
$ git branch -d feat
Deleted branch feat (was 1b95c22).

どこにいても同じ結果にするには、origin/main に取り込み済みと確かめたものだけを -D で消す。

git branch --merged origin/main --format='%(refname:short)' |
  grep -vxE 'main|master|develop' | xargs -r git branch -D

SHA で比べるので、この一覧にも「作っただけ」のブランチが入る。origin/main からコミットせずに作った fresh も消えた。

$ git branch --no-track fresh origin/main
$ git switch -q other
$ git branch --merged origin/main --format='%(refname:short)'
feat2
fresh
main
$ git branch --merged origin/main --format='%(refname:short)' | grep -vxE 'main|master|develop' | xargs -r git branch -D
Deleted branch feat2 (was 40634da).
Deleted branch fresh (was 46a6cde).
  • PITFALL: -d を並べたスクリプトが set -e だと、1 本の not fully merged で残りの削除がすべて止まる

branch -D が守るのは checkout 中のブランチだけ#

git branch -D は、どこかの worktree で checkout 中のブランチを消さない ( git worktree の記事 の「1 つのブランチは 1 つの worktree でしか checkout できない」の節)。 default ブランチかどうかは見ないので、main はどこでも checkout されていなければ消える。

git init -q --bare -b main origin.git
git clone -q origin.git repo 2>/dev/null && cd repo
git commit -q --allow-empty -m init && git push -q origin main
git remote set-head origin -a >/dev/null
git worktree add -q ../wt -b feat
git switch -qc other
$ git branch -D feat
error: cannot delete branch 'feat' used by worktree at '<root>/wt'
$ git branch -D main
Deleted branch main (was 3234635).
$ git branch
+ feat
* other

<root> は作業したディレクトリの絶対パス。git branch の一覧で先頭に + が付くのは、別の worktree で checkout 中のブランチ。 消す前に、対象が default ブランチでないことを自分で確かめる。default ブランチの名前は origin/HEAD から引ける。

$ git symbolic-ref --short refs/remotes/origin/HEAD
origin/main
  • PITFALL: 消す前に「いま checkout しているブランチか」を git branch --show-current の出力と比べて除外するスクリプトは、detached HEAD (ブランチでなくコミットを直接 checkout した状態) で空文字を受け取る。exit 0 で終わるので失敗に見えない。空のときを別に扱う

patch の中身で比べる判定#

rebase・cherry-pick で取り込んだブランチは git cherry が - を付ける#

rebase も cherry-pick も別のコミットを作るので、ブランチの先頭は base の祖先にならない。 git cherry <base> <branch> は、ブランチのコミットごとに、同じ patch-id のコミットが base にあれば -、無ければ + を付ける。

git init -q -b main demo && cd demo
git commit -q --allow-empty -m init
printf '1\n2\n3\n' > f && git add f && git commit -qm base
git switch -qc topic
echo 1 >> a && git add a && git commit -qm "topic: add a"
echo 1 >> b && git add b && git commit -qm "topic: add b"
git switch -q main
echo 1 >> m && git add m && git commit -qm "main: add m"
git cherry-pick topic~1 topic >/dev/null
$ git branch --merged main
* main
$ git merge-base --is-ancestor topic main; echo $?
1
$ git rev-list --count main..topic
2
$ git cherry -v main topic
- eb25241c6e847d892feb3128e4daf06066f5c9d0 topic: add a
- f741d42f8d1a566e5a692a9ce984c005d7d6d281 topic: add b

git cherry main topic | grep '^+' が何も出さなければ、base に無い変更は無い。ただし、作っただけのブランチも何も出さない ( 前提 の表)。

取り込むときに競合を手で直したコミットは、差分が変わるので patch-id も変わり、+ のまま出る。

git switch -qc topic2 main~2
sed -i '2s/.*/two-topic/' f && git commit -qam "topic2: edit line 2"
git switch -q main
sed -i '2s/.*/two-main/' f && git commit -qam "main: edit line 2"
git cherry-pick topic2 >/dev/null 2>&1                  # 競合で止まる
printf '1\ntwo-merged\n3\n' > f && git add f && GIT_EDITOR=true git cherry-pick --continue >/dev/null
$ git cherry -v main topic2
+ 7f00f27fceafad508e5f95d8e86b1f30fa0f77fb topic2: edit line 2

- は「同じ差分のコミットが base の履歴に 1 度入った」ことしか表さない。取り込んだ行を後から base で書き換えても - のまま。

git switch -qc topic3 main
echo x=1 >> c && git add c && git commit -qm "topic3: add c"
git switch -q main
echo 2 >> m && git add m && git commit -qm "main: m に 2"
git cherry-pick topic3 >/dev/null
sed -i 's/x=1/x=2/' c && git commit -qam "main: x=2"
$ git cherry -v main topic3
- 0976111f5114b5f377f6f4b4647f65b76c41776d topic3: add c
$ git show main:c
x=2
$ git log --oneline main -S'x=1'
afc3f12 main: x=2
00306bb topic3: add c

git log -S'<文字列>' は、その文字列の出現数を変えたコミットを出す。取り込んだコミットと、後で書き換えたコミットの両方が分かる。

  • PITFALL: + が出たら中身を読む。競合を直して取り込んだのか、取り込んでいないのかは、git cherry の出力では分からない

patch-id は rebase で変わらない#

ファイル x に 1 行足すコミットを、main が別のファイル y を変えた上へ rebase し、前後で 3 つの値を比べる。

show() {
  printf 'sha=%s tree=%s patch-id=%s\n' \
    "$(git rev-parse --short HEAD)" "$(git rev-parse --short 'HEAD^{tree}')" \
    "$(git show HEAD | git patch-id --stable | cut -c1-8)"
}
git init -q -b main demo && cd demo
git commit -q --allow-empty -m init
echo y > y && echo x > x && git add x y && git commit -qm base
git switch -qc topic
echo x2 >> x && git add x && git commit -qm "topic: x に 1 行"
show                                    # rebase の前
git switch -q main
echo y2 >> y && git add y && git commit -qm "main: y に 1 行"
git switch -q topic
git rebase -q main
show                                    # rebase の後
sha=7a3dff1 tree=7213257 patch-id=fa404182
sha=35edc87 tree=784ba49 patch-id=fa404182

tree は main 側の y を取り込んだので変わり、patch-id は変わらない。

ブランチ全体の差分を渡すと、コミットの切り方が違っても、最終的な差分が同じなら同じ値になる。 topic-split は、同じ 1 行を 2 本のコミットで足したブランチ。

git switch -qc topic-split main
echo x2-wip >> x && git add x && git commit -qm "topic-split: 仮の行"
sed -i 's/x2-wip/x2/' x && git commit -qam "topic-split: 行を直す"
$ git diff main topic | git patch-id --stable
fa404182347d920a3dcff43ebce3f7656587061b 0000000000000000000000000000000000000000
$ git log --oneline main..topic-split
5cc1713 topic-split: 行を直す
123b2b1 topic-split: 仮の行
$ git diff main topic-split | git patch-id --stable
fa404182347d920a3dcff43ebce3f7656587061b 0000000000000000000000000000000000000000

stacked PR は、下の PR のブランチから上の PR のブランチを切り、PR を積み重ねて出す運用。 下の PR がマージされた後に上の PR を新しい main へ rebase すると、上の PR のコミットの SHA は変わる。 patch-id が rebase の前と同じなら、上の PR が入れる差分は変わっていないので、rebase の前に流したテストやレビューの結果を持ち越せるかの目安になる。

空白だけが違う 2 つの変更は、既定では同じ値になり、--verbatim で別の値になる。git cherry も同じ変更として扱う。

git switch -qc sp1 main && echo 'a b' >> x && git add x && git commit -qm sp1
git switch -qc sp2 main && echo 'a    b' >> x && git add x && git commit -qm sp2
$ git show sp1 | git patch-id --stable | cut -c1-8
f3b9c4ca
$ git show sp2 | git patch-id --stable | cut -c1-8
f3b9c4ca
$ git show sp1 | git patch-id --verbatim | cut -c1-8
ff14d359
$ git show sp2 | git patch-id --verbatim | cut -c1-8
35570461
$ git cherry -v sp2 sp1
- c7bfc3b616e942909ece92bb0e298101f79e8c98 sp1
  • PITFALL: patch-id が言うのは「同じパッチか」だけ。base 側で呼び出し先・依存のバージョン・設定・DB スキーマが変われば、同じパッチでも挙動は変わる。マージ後の状態を確かめるなら、GitHub の merge queue のように、最新の base に当てた状態で必須チェックを回す

ブランチを消した後は、merge コミットの題名しか残らない#

ブランチを消すと ref が無くなり、残るのは merge コミットの題名だけ。 git merge は Merge branch '<branch>' を、GitHub の PR の merge は Merge pull request #N from <owner>/<branch> を題名にする。

取り込み方の違う 4 本を取り込んでから、ブランチを全部消した。by-pr は GitHub が作る題名を git merge -m で真似たもの。

git init -q -b main demo && cd demo
git commit -q --allow-empty -m init
git switch -qc by-merge && echo 1 >> m && git add m && git commit -qm "by-merge: 1"
git switch -q main && git merge -q --no-ff --no-edit by-merge
git switch -qc by-squash && echo 1 >> s && git add s && git commit -qm "by-squash: 1"
git switch -q main && git merge -q --squash by-squash >/dev/null && git commit -qm "by-squash (squash merge)"
git switch -qc by-ff && echo 1 >> f && git add f && git commit -qm "by-ff: 1"
git switch -q main && git merge -q --ff-only by-ff
git switch -qc by-pr && echo 1 >> p && git add p && git commit -qm "by-pr: 1"
git switch -q main && git merge -q --no-ff -m "Merge pull request #7 from someone/by-pr" by-pr
git branch -qD by-merge by-squash by-ff by-pr
$ git log --merges --format=%s main
Merge pull request #7 from someone/by-pr
Merge branch 'by-merge'

ブランチ名 $b で探す:

git log --merges --format=%s main |
  grep -E "^Merge (branch '$b'|pull request #[0-9]+ from [^/]+/$b)\$"

by-merge と by-pr は見つかり、by-squash と by-ff は grep が 1 で終わる。

  • PITFALL: squash merge と fast-forward は merge コミットを作らないので、題名からは拾えない

tree で比べる: squash の前と後で中身が同じか#

手元で複数のコミットを 1 本にまとめる (squash する) には git reset --soft <commit> を使う。 --soft はブランチの先頭だけを <commit> に戻し、index と作業ツリーはそのまま残す。戻したコミットの変更はすべて staged のまま残るので、続けて git commit すると 1 本のコミットになる。

squash した後は、作業前に打ったタグと HEAD の tree を比べる。 コミットを何本に分けても、最終的な tree が同じなら差分は 0 になる。

git tag backup/pre-squash               # 作業前
# ... squash する ...
git diff --stat --exit-code backup/pre-squash HEAD   # 0 なら tree が一致
git status --porcelain                  # 空であること
# 失敗したら git reset --hard backup/pre-squash

git diff はコミット同士を比べるので、作業ツリーに残った、どのコミットにも入っていないファイルは見ない。それを見るのが git status --porcelain。

feat ブランチに 3 本のコミット (f に 2 行、新しいファイル n) を積み、タグを打ってから squash する。 作業ツリーには、squash したコミットに入れるつもりで add していない new.txt がある。

git init -q -b main demo && cd demo
git commit -q --allow-empty -m init
echo 1 > f && git add f && git commit -qm base
git switch -qc feat
echo 2 >> f && git add f && git commit -qm "feat: f に 2"
echo 1 >> n && git add n && git commit -qm "feat: n を足す"
echo 3 >> f && git add f && git commit -qm "feat: f に 3"
git tag backup/pre-squash
echo wip > new.txt
git reset -q --soft main && git commit -qm "feat: f と n"
$ git diff --stat --exit-code backup/pre-squash HEAD
$ git status --porcelain
?? new.txt

git diff は終了コード 0 で何も出さない。new.txt に気づけるのは git status だけ。

mixed reset (git reset の既定) は、ブランチの先頭と index を戻し、作業ツリーだけを残す。戻したコミットの変更は unstaged になり、ブランチで新しく足したファイル n は untracked (git が追跡していないファイル) に戻る。 mixed reset で squash し直し、git add -u (追跡中のファイルの変更だけを add する) で commit すると、n はコミットから落ちる。こちらは両方に出る。

$ git diff --stat --exit-code backup/pre-squash HEAD
 n | 1 -
 1 file changed, 1 deletion(-)
$ git status --porcelain
?? n
  • PITFALL: 最終の tree が一致しても、途中のコミットが正しいことは何も保証されない。squash した後に 2 本に分け直し、1 本目に n が入っていなくても、タグとの差分は 0 になる

取り込む前に競合を調べる: git merge-tree --write-tree#

git merge-tree --write-tree A B は、作業ツリーと index に触れずに 2 つのブランチをマージした tree を作る。競合があれば 1、無ければ 0 で終わる。 複数の PR が互いに競合するかを、checkout せずに調べられる。

mk() { git switch -qc "$1" main && printf '%s\n' "$3" >> "$2" && git add "$2" && git commit -qm "$1"; }
git init -q -b main demo && cd demo
git commit -q --allow-empty -m init
echo a > log.txt && git add log.txt && git commit -qm base
mk p1 new.txt one      # 同じパスを別の中身で足す
mk p2 new.txt two
mk p3 new.txt one      # p1 とバイト単位で同じ中身
mk q1 log.txt q1       # 既存ファイルの末尾への追記どうし
mk q2 log.txt q2
mk r1 r1.txt r1        # 1 件 1 ファイル
mk r2 r2.txt r2
git switch -q main
組み合わせgit merge-tree --write-tree A B >/dev/null の終了コード
p1 p2 (同じパスを別の中身で足す)1
p1 p3 (同じパスを同じ中身で足す)0
q1 q2 (同じファイルの末尾に追記)1
r1 r2 (別々のファイルを足す)0

--name-only を付けると、1 行目にマージ結果の tree、続いて競合したファイル名と理由を出す。

$ git merge-tree --write-tree --name-only q1 q2
e0d4a897e15d55a95c970194b2475a9680f8504b
log.txt

Auto-merging log.txt
CONFLICT (content): Merge conflict in log.txt
$ git status --porcelain
$ git branch --show-current
main

既存ファイルの末尾への追記どうしは競合する。並行して足すものは 1 件 1 ファイルに分ける。

競合が無いことは、マージ結果が正しいことを意味しない。片方が関数 quote を shell_quote に改名し、もう片方が quote を呼ぶ b.sh を足すと、競合せずにマージでき、結果の tree に旧名の呼び出しが残る。

printf 'quote() { printf "%%s" "$1"; }\n' > lib.sh && git add lib.sh && git commit -qm lib
git switch -qc rename
printf 'shell_quote() { printf "%%q" "$1"; }\n' > lib.sh && git commit -qam "rename: quote を shell_quote に"
git switch -qc caller main
printf '. ./lib.sh\nquote "$x"\n' > b.sh && git add b.sh && git commit -qm "caller: b.sh"
git switch -q main
$ git merge-tree --write-tree rename caller >/dev/null; echo $?
0
$ git grep -nw quote $(git merge-tree --write-tree rename caller)
c7024762c5f78d226bfdff421a4f9a9bc983d4a2:b.sh:2:quote "$x"

rebase でも同じことが起きる ( git rebase の記事 の「競合の解消は、競合した行にしか効かない」の節)。

  • PITFALL: 終了コードで分かるのは競合の有無だけ。マージ後の tree でテストを流す
