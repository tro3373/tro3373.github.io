bash の read と $(...) が削る空白と改行

2026-11-26 ·  2026-11-26 · 10 分 · 2026 文字

結論#

  • bash が受け取ったテキストは、read、$(...)、<<<、heredoc を通るたびに形が変わる。どれもエラーにならず、終了コードも 0 のまま
  • read は行頭と行末の空白とタブを落とし、最初の改行で読み終わり、引用符は外さない。1 行をそのまま受けるなら IFS= read -r v。複数行は、stdin が pipe かファイルのときだけ cat で読む (相手が閉じない socket では cat が戻らない)
  • while-read ループの本体で stdin を読むコマンドは、ループの残りの行を読む。ループの入力は fd 3 に分ける。stdin が /dev/null のテストでは read が待たずに戻るので、「端末から起動したときだけ Enter を待つ」の判定 [[ -t 0 ]] を消しても、テストが通る
  • $(...) は末尾の改行をすべて落とし、<<< は 1 つ足す。末尾まで正確に扱う値はファイルで渡し、cmp で比べる
  • heredoc は区切りを引用符で囲んでも、本文中に区切りと同じ行があればそこで閉じる。第三者が書いた本文は、スクリプトの文面に書き写さずにパイプで渡す

以下は GNU bash 5.3.20 / jq 1.8.2 / curl 8.23.0 / GNU coreutils 9.12 / Linux x86_64 で実測した。

前提: 入力の形を変える 4 つの書き方#

bash のスクリプトがテキストを受け渡すとき、境目は次の 4 つの書き方で決まる。 stdin (標準入力) は、コマンドが入力を読む先で、パイプやファイルのリダイレクトでつなぎ替える。 プロセスが開いている入出力には番号 (fd、ファイル記述子) が付き、0 が stdin、1 が stdout、2 が stderr にあたる。

書き方移す向き変えること
read -r vstdin の 1 行から変数へ行頭と行末の空白とタブを落とす。2 行目以降を読まない。引用符を外さない
v=$(cmd)cmd の出力から変数へ末尾の改行をすべて落とす
cmd <<<"$v"変数から stdin へ末尾に改行を 1 つ足す
cmd <<'EOF' から EOF までスクリプトの文面から stdin へ本文中の EOF だけの行で閉じる
  • read は、stdin から 1 行読み、IFS で分けて変数に入れる組み込みコマンド。IFS は単語の区切りに使う文字の一覧で、既定は空白・タブ・改行
  • $(cmd) (コマンド置換) は、cmd の出力を文字列にして、その場に埋める
  • <<< (here-string) は、右に書いた文字列を stdin として渡す
  • heredoc は、<<EOF の次の行から EOF だけの行までを stdin として渡す

以下の例の { ...; } は、複数のコマンドをまとめて 1 つのパイプの読み手にする書き方。 read には -r を付ける。-r は \ をエスケープとして扱わない指定で、付けないと入力の a\tb が atb になる。

printf 'a\\tb\n' | { read v; printf '[%s]\n' "$v"; }
printf 'a\\tb\n' | { read -r v; printf '[%s]\n' "$v"; }
[atb]
[a\tb]

read は行頭と行末の空白を落とす#

read は行を IFS で単語に分ける。受ける変数が 1 つでも、行頭と行末にある IFS の空白とタブは取り除かれる。行の途中の空白は残る。 IFS= read と書くと、IFS を空にしてその read だけを動かす。区切りが無くなるので、行がそのまま入る。スクリプトの IFS は変わらない。

printf '  example  \n' | { read -r v; printf '[%s]\n' "$v"; }
printf '  example  \n' | { IFS= read -r v; printf '[%s]\n' "$v"; }
printf '\tpass word \n' | { read -r v; printf '[%s]\n' "$v"; }
printf '\tpass word \n' | { IFS= read -r v; printf '[%s]\n' "$v"; }
printf 'a  b\n' | { read -r v; printf '[%s]\n' "$v"; }
[example]
[  example  ]
[pass word]
[	pass word ]
[a  b]

パスワードや token を read で受けるときに当たる。

  • PITFALL: read -s (打った文字を画面に出さない) で受けていると、前後に空白を含む値を正しく打っても認証が落ち、何が違うのかを画面で確かめられない

タブ区切りの行を IFS=$'\t' read -r a b c で列に分けると、空の列が詰まって値が前へずれる。 タブも IFS の空白として扱われ、連続が 1 つの区切りになるため。対策は jq の入力・真偽・シェルとの受け渡し に書いた。

read は引用符を外さない#

引用符を外すのは、bash がスクリプトのコマンド行を構文解析するときだけ。read は入力を文字として読むので、" は値に残る。 一覧のファイルから method url の形の行を読んで curl に渡すと、curl は引用符の付いた URL を拒否する。

read -r cmd url <<<'get "http://h/x"'; printf 'cmd=[%s] url=[%s]\n' "$cmd" "$url"
read -r cmd url <<<'get "http://h/x"'; curl -sS -o /dev/null "$url"; echo "rc=$?"
printf '[%s]\n' get "http://h/x"
cmd=[get] url=["http://h/x"]
curl: (3) URL rejected: Port number was not a decimal number between 0 and 65535
rc=3
[get]
[http://h/x]

3 つ目は、同じ文字列をスクリプトに直接書いた場合で、引用符は bash が外す。

一覧には引用符を書かない。 read は最後の変数に、残りの語を間の空白ごと入れる。URL を行の最後の列にすれば、空白を含んでも 1 つの値で受けられる。 引用符を書いた一覧を読むなら、両端の " を外す。${url#\"} は先頭の " を、${url%\"} は末尾の " を 1 つ取り除く。

read -r cmd url <<<'get http://h/a b'; printf 'cmd=[%s] url=[%s]\n' "$cmd" "$url"
read -r cmd url <<<'get "http://h/x"'; url=${url#\"}; url=${url%\"}; printf 'url=[%s]\n' "$url"
cmd=[get] url=[http://h/a b]
url=[http://h/x]
  • PITFALL: 引用符を付けずに $url と展開すると、今度は値の空白で 2 つの引数に分かれる
read -r cmd url <<<'get "http://h/a b"'; printf '[%s]\n' $url
["http://h/a]
[b"]

read は 1 行目で読み終わる#

read は 1 行を読むコマンドで、最初の改行で読み終わる。残りの行があってもエラーにせず、終了コード 0 を返す。

printf 'first\nsecond\n' | { IFS= read -r v; echo "rc=$? [$v]"; }
printf '%s\n' '{' '  "k": "v"' '}' | { IFS= read -r v; echo "rc=$? [$v]"; }
rc=0 [first]
rc=0 [{]

秘密の値を伏せて入力させるスクリプト (read -s) に、鍵ファイルや JSON をパイプで流すと当たる。先頭の 1 行だけの値が、成功の表示のまま登録される。

stdin が端末のときだけ read で伏せて読み、pipe かファイルなら cat で丸ごと読む。 [[ -t 0 ]] は stdin (fd 0) が端末なら、-p /dev/stdin は pipe なら、-f /dev/stdin は通常のファイルなら真になる。read の -p は、入力の前に出す案内の文字列。 どれでもない stdin では読まずに止める理由は、次の節に書く。

read-input.sh:

#!/usr/bin/env bash
# 値を、端末なら伏せて打たせ、pipe かファイルなら stdin から丸ごと読む。それ以外は読まずに止める
if [[ -t 0 ]]; then
  IFS= read -rsp 'value: ' v
elif [[ -p /dev/stdin || -f /dev/stdin ]]; then
  v=$(cat)
else
  echo "stdin が端末でも pipe でもファイルでもない" >&2
  exit 2
fi
printf 'got %d bytes\n' "${#v}"
printf 'first\nsecond\n' | bash read-input.sh
bash read-input.sh </dev/null; echo "rc=$?"
got 12 bytes
stdin が端末でも pipe でもファイルでもない
rc=2

2 行とも読めた。12 バイトは first と改行と second で、末尾の改行は $(cat) が落とした (後の節で扱う)。

端末でない stdin は、閉じない socket のこともある#

[[ -t 0 ]] が偽になるのは、端末以外のすべて。pipe とファイルのほかに、/dev/null と socket でも偽になる。 「端末でなければ cat で読む」と書くと、相手が閉じない socket が stdin のとき、cat は EOF (入力の終わり) が来ないので戻らない。cat が読み終わるのは、書き手が全員閉じて EOF が届いたとき。 コーディングエージェントのコマンド実行ツールやプロセス管理ツールには、stdin に socket を渡して閉じないものがある。 端末から起動すると stdin は端末なので cat に入らず、手元では再現しない。 呼び出し元が何を渡すかを当てにせず、読む側で判定する。

下の表は、stdin の種類ごとに [[ ... ]] の判定を並べたもの。-c は文字デバイス、-S は socket なら真になる。端末は script (疑似端末を作って中でコマンドを動かす util-linux のコマンド) の中で測った。

stdin-t 0-p /dev/stdin-f /dev/stdin真になる他の判定
端末ynn-c
pipenyn
< filenny
heredoc (小)nyn
heredoc (200KB)nny
here-stringnyn
/dev/nullnnn-c
socketnnn-S

heredoc と here-string は、bash 5.1 以降、大きさで pipe か一時ファイルかが変わる。-p だけで判定すると、< file と大きな heredoc を読まない ( bash のパイプが返す終了コードと SIGPIPE )。

閉じない socket は、python3 の socket.socketpair() で作れる。互いにつながった socket を 2 つ作り、片方を stdin にして bash を起動し、もう片方は閉じずに持っておく。 timeout=3 は、3 秒で戻らなければ例外にする指定。

python3 -c 'import socket,subprocess; a,b=socket.socketpair(); subprocess.run(["bash","-c","[[ ! -t 0 ]] && cat; echo done"], stdin=b, timeout=3)' 2>&1 | tail -n 1
python3 -c 'import socket,subprocess; a,b=socket.socketpair(); subprocess.run(["bash","read-input.sh"], stdin=b, timeout=3); print("returned")'
subprocess.TimeoutExpired: Command '['bash', '-c', '[[ ! -t 0 ]] && cat; echo done']' timed out after 2.9999695229998906 seconds
stdin が端末でも pipe でもファイルでもない
returned

1 つ目は cat が戻らず、echo done まで進まなかった。読むのを pipe とファイルに絞った read-input.sh は、socket では読まずに抜けた。

  • PITFALL: 呼び出す側で </dev/null を付けても止まらなくなるが、全部の呼び出しに付ける必要がある。読む側で判定を絞る方が漏れない

ループの本体のコマンドは、ループの入力を読む#

while read -r x; do ...; done < file のリダイレクトは、ループ全体に掛かる。ループの本体のコマンドも、同じ stdin を引き継ぐ。 本体で stdin を読むコマンド (cat、ssh、ffmpeg、-u を付けない read など) は、ループがまだ読んでいない行を読む。読まれた行は、ループに回らない。

< <(items) は、items の出力をループの stdin にする書き方。 <(items) (プロセス置換) が items の出力を読めるファイルの名前に置き換わり、< がそれを stdin にする。 名前はファイルでも、その実体は items の出力につながったパイプなので、ループの stdin はパイプになる。

本体で stdin を読むコマンドの例として、ログを出す関数 log を本体で呼ぶ。 log は、stdin がパイプならその中身も cat で読んでログに混ぜる。[[ -p /dev/stdin ]] は、stdin がパイプなら真になる。 ループの stdin はパイプで、本体の log もそれを引き継ぐので、log の cat がループの入力を読む。

log() { if [[ -p /dev/stdin ]]; then printf 'LOG: %s / %s\n' "$*" "$(cat - | tr '\n' ' ')"; else printf 'LOG: %s\n' "$*"; fi; }
items() { printf 'a\nb\nc\nd\n'; }
while read -r x; do log "item $x"; done < <(items)
LOG: item a / b c d

1 周目の log の cat が b c d を読み、ループは 1 回で終わった。

ループの入力は、まだ使っていない fd 3 に分ける。 3< <(items) で items の出力を fd 3 に開き、read -r x <&3 で fd 3 から読む。read -r -u 3 x と書いても同じ。 本体のコマンドの stdin は、ループの外の stdin のまま変わらない。

while read -r x <&3; do log "item $x"; done 3< <(items)
LOG: item a
LOG: item b
LOG: item c
LOG: item d

確認の read が、一覧の次の行を答えにする#

選んだ複数件をループで処理し、その中で 1 件ずつ確認を取ると、一覧の次の行が確認の答えとして読まれる。

confirm() { read -r ans; echo "ans=[$ans]"; }
while read -r x; do echo "item=$x"; confirm; done < <(printf 'a\nb\n')
item=a
ans=[b]

b は確認の答えになり、ループでは処理されない。 一覧を fd 3 に逃がすと、確認はループの外の stdin から読む。printf 'y\ny\n' | で答えを渡すテストも通る。

printf 'y\ny\n' | { while read -r x <&3; do echo "item=$x"; confirm; done 3< <(printf 'a\nb\n'); }
item=a
ans=[y]
item=b
ans=[y]
  • PITFALL: 確認を read -r ans </dev/tty (端末から直接読む) に替えても一覧の行は読まれなくなるが、パイプで答えを渡すテストが通らない。端末の無いところで動かすと /dev/tty を開けず、答えは空になる (下は 1 行の bash -c で実行した出力)
confirm() { read -r ans </dev/tty; echo "ans=[$ans]"; }; printf 'y\ny\n' | { while read -r x <&3; do echo "item=$x"; confirm; done 3< <(printf 'a\nb\n'); }
item=a
bash: line 1: /dev/tty: No such device or address
ans=[]
item=b
bash: line 1: /dev/tty: No such device or address
ans=[]

本体のコマンドの stdin を /dev/null にする#

ループの入力を fd 3 に分けずに、stdin を読む本体のコマンドだけをループの入力から切り離すなら、そのコマンドの stdin を /dev/null にする。

printf 'l1\nl2\nl3\n' > in.txt
while read -r l; do echo "$l"; cat >/dev/null; done < in.txt
while read -r l; do echo "$l"; cat >/dev/null </dev/null; done < in.txt
l1
l1
l2
l3
  • PITFALL: テストでループの本体から呼ぶコマンドをスタブ (本物のコマンドの代わりに置く偽のコマンド) に替えたとき、スタブが stdin を読むと、テストしたいスクリプトの挙動でなくスタブのせいでループの行が消え、テストの結果が当てにならない
  • PITFALL: ループを fd 3 に分けても、スクリプト自体が stdin をパイプで受けて起動されたとき (... | bash setup.sh や、cron でパイプにつないだ実行) は、ログ関数がそのパイプを読む。stdin の有無で挙動を変える関数は、表示する中身を引数で受ける形にする
printf 'piped\n' | bash -c 'log() { if [[ -p /dev/stdin ]]; then printf "LOG: %s / %s\n" "$*" "$(cat - | tr "\n" " ")"; else printf "LOG: %s\n" "$*"; fi; }; items() { printf "a\nb\n"; }; while read -r x <&3; do log "item $x"; done 3< <(items)'
LOG: item a / piped 
LOG: item b /

stdin が /dev/null の read は待たずに戻る#

read は EOF を受けると、何も読まずに 1 を返す。/dev/null は読むとすぐ EOF になるので、stdin が /dev/null の read は待たずに戻る。 EPOCHREALTIME は、bash が持つ現在時刻 (秒。小数点以下はマイクロ秒) の変数。

s=$EPOCHREALTIME; read -r _ </dev/null; rc=$?; printf 'rc=%d elapsed=%.3fs\n' "$rc" "$(bc <<<"$EPOCHREALTIME - $s")"
rc=1 elapsed=0.001s

テストを実行する仕組み (test runner) は、テストの stdin を /dev/null にすることが多い。 端末から起動したときだけ Enter を待つスクリプトで、その判定 [[ -t 0 ]] を消しても、テストでは read がすぐ戻り、止まらずに通る。

good.sh:

#!/usr/bin/env bash
# 端末から起動したときだけ Enter を待つ
echo start
[[ -t 0 ]] && read -r -p 'Enter で続行: ' _
echo done

bad.sh は、good.sh から [[ -t 0 ]] && を消したもの。

bash good.sh </dev/null; echo "good rc=$?"
bash bad.sh </dev/null; echo "bad rc=$?"
start
done
good rc=0
start
done
bad rc=0

判定が効いているかを確かめるなら、何も書き込まない stdin と timeout を組む。 < <(sleep 10) は、10 秒のあいだ何も書かずに開いているパイプを stdin にする。判定を消した版は read で止まり、timeout 2 が 2 秒で止めて 124 を返す。

timeout 2 bash good.sh < <(sleep 10); echo "good rc=$?"
timeout 2 bash bad.sh < <(sleep 10); echo "bad rc=$?"
start
done
good rc=0
start
bad rc=124

read が EOF で返す 1 は、set -e (失敗したコマンドでスクリプトを止める設定) の下ではスクリプトを止める。 read ... || true が EOF を握り潰し、非対話の実行で確認を素通りさせる件は bash の set -e が効かない場所と効きすぎる場所 に書いた。 read -r v || v="" も同じで、EOF と空の Enter を区別できなくなる。

$(...) は末尾の改行をすべて落とす#

コマンド置換は、仕様として出力の末尾の改行をすべて取り除く。途中の改行は残る。

v=$(printf 'abc\n\n'); printf '%s' "$v" | od -c
v=$(printf 'a\n\nb\n'); printf '%s' "$v" | od -c
0000000   a   b   c
0000003
0000000   a  \n  \n   b
0000004

stdin の本文を変数に受けてから別のコマンドへ渡すと、末尾が変わる。入力の末尾の改行が 0 個でも 1 個でも 2 個でも、出力は同じになる。

printf 'x' | bash -c 'b=$(cat); printf "%s\n" "$b"' | od -c
printf 'x\n' | bash -c 'b=$(cat); printf "%s\n" "$b"' | od -c
printf 'x\n\n' | bash -c 'b=$(cat); printf "%s\n" "$b"' | od -c
0000000   x  \n
0000002
0000000   x  \n
0000002
0000000   x  \n
0000002

秘密の値のように、末尾の改行も含めて正確に保存・比較したい値で当たる。 改行を含む値を弾く検査も、$(...) で受けた値では末尾の改行が見えないので通る。

v=$(printf 'secret\n'); [[ $v == *$'\n'* ]] && echo has-newline || echo no-newline
no-newline

末尾を保つなら、出力の後ろに印の 1 文字を足し、受けた後で外す。${v%x} は、末尾の x を 1 つ取り除く。

v=$(printf 'abc\n\n' && printf x); v=${v%x}; printf '%s' "$v" | od -c
0000000   a   b   c  \n  \n
0000005
  • PITFALL: 印を && でなく ; でつなぐと、$(...) の終了コードは最後の printf の 0 になり、前のコマンドの失敗が消える
v=$(false; printf x); echo "rc=$?"
v=$(false && printf x); echo "rc=$? v=[$v]"
rc=0
rc=1 v=[]

変数を経由しないなら、一時ファイルに受けてリダイレクトで渡す。

tmp=$(mktemp); printf 'x\n\n' | cat > "$tmp"; od -c < "$tmp"; rm -f "$tmp"
0000000   x  \n  \n
0000003
  • PITFALL: テストで期待値と実測値を両方 $(cat file) で比べると、末尾の改行の差が比べる前に消え、テストが通る。ファイル同士を cmp で比べる
printf 'x\n\n' > want.txt; printf 'x\n' > got.txt
[[ "$(cat want.txt)" == "$(cat got.txt)" ]] && echo same
cmp want.txt got.txt; echo "cmp rc=$?"
same
cmp: EOF on ‘got.txt’ after byte 2, line 1
cmp rc=1

<<< は末尾に改行を 1 つ足す#

here-string は、本文に改行を 1 つ足して stdin に渡す。本文が既に改行で終わっていても、もう 1 つ足す。

cat <<<'abc' | od -c
v=$'abc\n'; cat <<<"$v" | od -c
0000000   a   b   c  \n
0000004
0000000   a   b   c  \n  \n
0000005

here-string で渡した本文を保存し、後から文字列で比べると当たる。 jq -Rs は stdin 全体を 1 つの文字列として読むので、足された改行も本文に入る。

jq -Rs 'endswith("abc")' <<<'abc'
jq -Rs 'rtrimstr("\n") | endswith("abc")' <<<'abc'
printf '%s' 'abc' | jq -Rs 'endswith("abc")'
false
true
true

改行を足したくないなら printf '%s' "$v" | で渡す。受ける側で落とすなら、jq では rtrimstr("\n") を使う。

  • PITFALL: テストで本文を末尾に改行の無いファイルから渡すと比較が通り、本番の <<< で渡す経路でだけ比較が常に false になる
  • PITFALL: $(...) で受けた一覧を wc -l <<<"$list" で数えると、$(...) が落とした末尾の改行を <<< が 1 つ戻すので、行数は合う。一覧が空のときだけ、改行が 1 つ渡って 1 になる
list=$(printf 'a\nb\n'); wc -l <<<"$list"
list=$(printf ''); wc -l <<<"$list"
list=$(printf ''); if [[ -z $list ]]; then echo 0; else wc -l <<<"$list"; fi
2
1
0

heredoc は区切りを引用符で囲んでも、本文中の区切りの行で閉じる#

heredoc の区切りを引用符で囲む (<<'EOF') と、本文の $ や ` を展開しない。 引用符が止めるのは展開だけで、終端の検出は止めない。終端は、区切りと同じ文字列だけの行が来たところで決まる。

cat inj.sh
bash inj.sh; echo "rc=$?"
cat <<'EOF'
line1
EOF
echo INJECTED
EOF
line1
INJECTED
inj.sh: line 5: EOF: command not found
rc=127

3 行目の EOF で heredoc が閉じ、4 行目の echo INJECTED がコマンドとして実行された。 5 行目の EOF は、EOF という名前のコマンドとして実行され、見つからずに 127 になった。

起きるのは、本文をスクリプトやコマンドの文面に直接書き写したとき。 issue の本文など第三者が書ける文字列を cat <<'EOF' と EOF の間に貼ってシェルに渡すと、本文に EOF だけの行があれば、その後ろの行がコマンドとして実行される。 コーディングエージェント (LLM) に本文を heredoc へ書き写させ、コマンドを組ませる手順も同じで、本文次第で任意のコマンドが実行される。

変数に入れた本文を heredoc の中で展開した値と、パイプで渡した本文は、終端の検出に使われない。

var.sh:

# 本文を変数で持ち、heredoc の中で展開する
body=$'line1\nEOF\necho INJECTED'
cat <<EOF
$body
EOF
echo ---
# 本文をパイプで渡す
printf '%s\n' "$body" | cat
bash var.sh
line1
EOF
echo INJECTED
---
line1
EOF
echo INJECTED

第三者の本文は、取ってきたコマンドの出力をそのまま次のコマンドへパイプで渡し、スクリプトの文面を通さない。 GitHub の issue なら gh api ... --jq .body | cmd の形にする。gh api は GitHub の API を呼ぶコマンドで、--jq .body は応答の body の項目だけを出す。
