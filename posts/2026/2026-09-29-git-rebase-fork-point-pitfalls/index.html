git rebase が警告なしに動かすものと残すもの

2026-09-29 ·  2026-09-29 · 7 分 · 1435 文字

結論#

  • git rebase main は、ブランチにあって main に無いコミットを、main の先頭へ 1 本ずつ cherry-pick し直す。git はブランチの派生元を記録しないので、どこから先を載せるかは毎回コミットグラフから求める
  • rebase の後は git merge-base main HEAD が main の先頭を返す。元の分岐点を後で使うなら rebase の前に控える
  • 競合中の --ours は main 側、--theirs は自分のコミット。merge と逆になる
  • 競合しなかったことは、整合していることを意味しない。main が入れた改名や規約は、競合しないファイルには届かない
  • squash merge の後や載せるコミットが 0 件のときは、どこから先を載せるかの推定がずれて、衝突やブランチ先頭の移動が起きる。--onto で起点を明示する
  • autostash の書き戻しが衝突しても、rebase も pull --ff-only も exit 0 で終わる

以下はすべて git 2.55.0 で実測した。pull.rebase や rerere.enabled などの利用者設定で結果が変わるので、GIT_CONFIG_GLOBAL=/dev/null で ~/.gitconfig を読ませずに実行している。

前提: rebase は分岐点から先を作り直す#

git rebase <upstream> は次の 4 段で動く (man git-rebase)。

  1. 今のブランチにあって <upstream> に無いコミットを並べる。<upstream> に同じ変更 (patch-id が一致するコミット) があるものは外す
  2. <upstream> の先頭を detach でチェックアウトする
  3. 並べたコミットを 1 本ずつ cherry-pick する
  4. ブランチをできあがった先頭へ付け替える

1 の範囲は git log <upstream>..HEAD と同じで、分岐点から先にあたる ( git logの「..」と「…」の違い )。

ブランチは 1 つのコミットを指すポインタでしかなく、どのブランチから切ったかは記録されない。 分岐点はその都度コミットグラフから計算する (git merge-base)。 ほかに手掛かりになるのはブランチの reflog に残る branch: Created from main~2 のような行だけで、これはローカル専用で clone には引き継がれず、既定 90 日で期限が切れる。 reflog を参照する git merge-base --fork-point も同じ制約を受ける。

以下の罠の多くは「分岐点はグラフから計算し直すもので、rebase で動き、squash で見失う」ことから来る。

rebase の前に控えるもの#

rebase の後は merge-base が base の先頭に移る#

rebase でブランチが main の先頭に載ると、共通の祖先も main の先頭になる。rebase の後に分岐点からの差分を取ると空になる。

OLD=$(git merge-base main HEAD)   # rebase の前に控える
git rebase main
git diff --name-status "$(git merge-base main HEAD)" main   # 空
git diff --name-status "$OLD" main                          # 今回取り込んだ main の変更

rebase の直後なら ORIG_HEAD が rebase 前の先頭を指すので、git merge-base main ORIG_HEAD でも元の分岐点が取れる。

「前回の追従以降に main で何が変わったか」を rebase の後で知りたい場面で効く。 翻訳や生成物のように base 側の変更を後追いで反映するブランチや、後述の規約の取りこぼしを探すときに要る。

  • PITFALL: ORIG_HEAD は reset や merge でも上書きされる。使うなら rebase の直後か、変数に控えておく
  • PITFALL: merge-base はブランチが分かれた位置でしかない。派生ファイルが元ファイルのどの版から作られたかは表さないので、同期した時点の sha を別に記録する (git config --local sync.base "$(git rev-parse main)" など)

載せるコミットが 0 件でも、ブランチの先頭は base まで進む#

$ git switch -c empty main~2    # main から 2 つ手前で切っただけのブランチ
$ git rebase main
Successfully rebased and updated refs/heads/empty.
$ git log -1 --format=%s
m3                              # main の先頭

固有のコミットが 0 件なら、「base の上に自分の分が載った状態」は base そのものになる。 誤ったベースへ rebase すると「コミットが消えた」ように見えるが、先頭が動いただけで何も失われていない。

戻すときは HEAD の reflog でなく、ブランチの reflog を使う。

$ git reflog -3
0a24bab HEAD@{0}: rebase (finish): returning to refs/heads/empty
0a24bab HEAD@{1}: rebase (start): checkout main
9d5b23b HEAD@{2}: checkout: moving from main to empty
$ git reflog -2 empty
0a24bab empty@{0}: rebase (finish): refs/heads/empty onto 0a24babd6d53def78b3ce9a6f1632b38d4e8282c
9d5b23b empty@{1}: branch: Created from main~2

rebase は HEAD の reflog に start / pick / finish を 1 行ずつ積むので、HEAD@{1} は rebase 前の位置ではない。 ブランチの reflog は rebase 1 回につき 1 行なので、git reset --hard empty@{1} (今いるブランチなら @{1}) で rebase 前に戻る。

  • PITFALL: reflog はローカル専用で push されない。どこからも辿れないコミットの reflog は既定 30 日で期限が切れ、その後の git gc で本体も消える。気づいたその日に戻す

競合の読み方#

競合中の --ours は base 側、--theirs は自分のコミット#

rebase は base の先頭をチェックアウトし、その上に自分のコミットを cherry-pick する。チェックアウトされている側が ours なので、merge と向きが逆になる。

git init -q -b main demo && cd demo
printf 'a\nb\nc\n' > f && git add f && git commit -qm base
git switch -qc feat && printf 'a\nFEAT\nc\n' > f && git commit -qam feat
git switch -q main && printf 'a\nMAIN\nc\n' > f && git commit -qam main
git switch -q feat
git rebase main                            # 競合で止まる
git checkout --ours f && sed -n 2p f       # MAIN
git checkout --theirs f && sed -n 2p f     # FEAT
feat にいて実行--ours--theirs
git merge mainfeat (FEAT)main (MAIN)
git rebase mainmain (MAIN)適用中の feat のコミット (FEAT)

競合マーカーの <<<<<<< HEAD 側も、rebase では main の内容になる。進行中の操作はファイルの有無で見分けられる。

test -d "$(git rev-parse --git-path rebase-merge)"     && echo rebase
test -d "$(git rev-parse --git-path rebase-apply)"     && echo "rebase --apply か am"
test -f "$(git rev-parse --git-path MERGE_HEAD)"       && echo merge
test -f "$(git rev-parse --git-path CHERRY_PICK_HEAD)" && echo cherry-pick
  • PITFALL: 手順書やスクリプトに ours / theirs をそのまま書くと、merge 用の手順を rebase に流用したときに、片側全採用で自分の変更が丸ごと消える。「base 側 / 持ち込む側」で書き、実行時に操作を判定して対応させる

add/add 競合は共通祖先が空になる#

両側が同じパスにファイルを新規追加すると、3-way merge の共通祖先は空になる。 差分が 1 行でも、どこまでを競合として見せるかは merge.conflictStyle で変わる。

1 から 10 の行を持つ new.txt を両側で追加し、main 側だけ 5 行目を FIVE にして git rebase main した結果:

merge.conflictStyle競合マーカーの範囲競合後の行数
merge (既定)5 行目だけ14
zdiff35 行目だけ (祖先の欄は空)15
diff3ファイル全体24

diff3 は、両側で一致する前後の行も競合の範囲に残す。共通祖先が空だと、ファイル全体が 1 つの競合になる。 diff3 を使っていると「1 行しか違わないのに全文が競合した」ように見える。

rebase で add/add が起きやすいのは、同じ内容のコミットを両側に持つブランチ同士。 patch-id が完全に一致するコミットは rebase が自動で外すので、競合の元になるのは外れずに残ったコミットだけになる。

$ git rebase main
warning: skipped previously applied commit 6651905
hint: use --reapply-cherry-picks to include skipped commits

どのコミットが対応し、どこが違うかは、rebase の前に git range-diff main...HEAD で見る。

  • PITFALL: 未 push のブランチ同士なら、rebase せずにブランチの指す先を付け替えるだけで済むことが多い。チェックアウトしていないブランチなら git branch -f main <commit> で、コミットもファイルも作らずに動かせる。外れたコミットは reflog から戻せる

ファイル移動の上に rebase すると、競合は移動先に寄る#

main で old.txt を pkg/new.txt へ移動し、feat では old.txt の 5 行目を編集していた場合。

main 側git rebase main の結果
移動だけ競合なし。feat の変更は pkg/new.txt に入る
移動 + 同じ行を編集pkg/new.txt の UU (both modified) 1 件。old.txt は残らない
移動 + ほぼ全行を書き換えold.txt の DU (deleted by us。rebase なので us は main 側)

rename 検出が、旧パスへの変更を新パスへの変更として扱う。 rename と判定されるのは内容の類似度が既定の 50% 以上のとき (git diff -M と同じ基準。merge では -X find-renames=<n> で変える)。 下回ると別ファイルの削除と追加として扱われ、旧パスの削除/変更の競合になる。このときは feat の変更を手で新パスへ移す。

競合を解いた pick のメッセージは rebase-merge/message で直せる#

競合で止まった pick のコミットメッセージは .git/rebase-merge/message に置かれ、git rebase --continue はここからメッセージを作る。 競合の解消でコミットの中身が変わったなら、--continue の前にこのファイルを書き換える。

# 競合を解消して git add した後
MSG=$(git rev-parse --git-path rebase-merge/message)
cat "$MSG"                              # 元のメッセージと "# Conflicts:" のコメント
echo "feat: rewritten message" > "$MSG"
git rebase --continue
git log --oneline -1                    # feat: rewritten message

競合しなかった箇所#

競合の解消は、競合した行にしか効かない#

3-way merge はテキストの重なりだけを見る。base が「関数を改名した」「エスケープ規則を統一した」という意味は、ブランチ側の新規ファイルのどの行とも重ならない。

git init -q -b main demo && cd demo
printf 'quote() { printf "%%s" "$1"; }\n' > lib.sh
printf '. ./lib.sh\nquote "$x"\n' > a.sh
git add -A && git commit -qm base
git switch -qc feat
printf '. ./lib.sh\nquote "$y"\n' > b.sh
git add -A && git commit -qm "feat: add b.sh"
git switch -q main
printf 'shell_quote() { printf "%%q" "$1"; }\n' > lib.sh
printf '. ./lib.sh\nshell_quote "$x"\n' > a.sh
git commit -qam "refactor: quote を shell_quote に改名"
git switch -q feat
FORK=$(git merge-base main HEAD)
git rebase main                   # 競合なしで成功する
git log --oneline "$FORK"..main   # main がこの間に入れた変更
git grep -nw quote                # b.sh:2:quote "$y" が残る

rebase は通り、b.sh を通るテストが無ければ CI も通る。 rebase の後に、分岐点から base の先頭までのコミットを読み、base が決めた規約がブランチ側の新規ファイルに当たっているかを grep で確かめる。 そのために rebase 前の分岐点が要る。

  • PITFALL: 最も見つけにくいのは文書と実装の食い違い。分岐した時点で正しかった doc コメントが、base の変更で誤りになる。コードは競合しないので rebase は競合を出さずに通り、テストも通る
  • PITFALL: 期待値の一覧を分岐時点で写したテストは、base が後から足した項目が抜けたまま通る

起点の推定がずれるとき#

squash merge された下段の上に載せるなら --onto で起点を明示する#

stacked PR で下段 b1 が squash merge されると、b1 のコミットは main 上で別のコミット 1 本になる。 上段 b2 を git rebase main すると、b2 に含まれる b1 のコミットも載せ直す対象に入る。

実測では b1 のコミット数で結果が分かれた。

b1 のコミットgit rebase main b2git rebase --onto main b1 b2
1 本成功 (squash コミットと patch-id が一致して外れる)成功
2 本 (同じ行を 2 回編集)競合 (UU f)成功

複数のコミットを 1 本に畳むと patch-id が変わるので、b1 の各コミットは「main に無いコミット」として扱われる。 main 上の最終形に途中の版を当てようとして競合する。 --onto <newbase> <oldbase> は「oldbase より先だけを newbase へ載せる」と明示し、推定を使わない。

# b1 = squash merge 済みの下段, b2 = 上段
git fetch origin
git rebase --onto origin/main b1 b2

git branch -d は squash / rebase merge したブランチを未マージと判定する#

-d は「ブランチの先頭が upstream (無ければ HEAD) から辿れるか」で判定する。 squash merge も rebase merge も main 側に新しいコミットを作るので、元のブランチの先頭はどこからも辿れない。

$ git branch -d b1    # main に squash merge 済み
error: the branch 'b1' is not fully merged

merge コミットで取り込み、base を pull 済みなら -d が通る。squash / rebase merge したブランチは -D で消す。 git branch --merged も同じ判定なので、マージ済みブランチを掃除するスクリプトは squash merge したブランチを拾わない。

rebase 後の --force-with-lease は、fetch の後なら --force と同じ#

期待値なしの --force-with-lease は「リモートが origin/<branch> の指すコミットのままなら上書きする」。 git fetch や git pull が origin/<branch> を更新した後は、手元に取り込んでいない他人のコミットがあっても上書きが通る。

他人が push した後に fetch だけして、取り込まずに書き換えたコミットを push した結果:

push のオプションexitリモートの履歴
--force-with-lease0mine base (他人のコミットが消える)
--force-with-lease --force-if-includes1other base (拒否)

--force-if-includes は、リモート追跡ブランチの先頭がローカルのブランチ (の reflog) から辿れるかを確かめ、取り込んでいなければ拒否する。

git push --force-with-lease --force-if-includes origin "$branch"
  • PITFALL: --force-with-lease=<branch>:<sha> で期待値を渡しても、その sha を今のリモートの先頭 (PR の head など) から取ったなら同じく通る。期待値をどこから取ったかで保護の意味が変わる

非対話で回す#

--autosquash は -i なしでも効く#

git commit --fixup=<TARGET>
git rebase --autosquash --autostash <TARGET>^

git 2.55.0 では、-i を付けなければ todo の編集画面は開かない (GIT_SEQUENCE_EDITOR=false を渡しても成功する)。 -i を付けたときは GIT_SEQUENCE_EDITOR=: で todo をそのまま受理させる。false のままだと exit 1 で止まる。

tip でないコミットは --amend で直せないので、fixup コミットを積んでから畳む。

  • 未コミットの変更があると error: cannot rebase: You have unstaged changes. で止まる。--autostash を付ける
  • PITFALL: 対象は fixup! の後ろと件名の完全一致、無ければ前方一致で探す。どの件名にも一致しないと、畳まれずに独立したコミットとして残り、rebase は成功で終わる。--fixup=<sha> で件名を自動で埋め、畳んだ後に git log で fixup! が残っていないか見る
  • PITFALL: 対象より後ろのコミットはすべて作り直されるので、push 済みなら force push が要る

autostash の書き戻しが衝突しても exit 0 で終わる#

rebase.autoStash / merge.autoStash が有効だと、git は「stash => 本体の操作 => stash pop」を行う。pop の衝突は本体の失敗として扱われない。

リモートが先行し、手元の未コミットの変更が同じ行を触っている状態で git pull --ff-only した結果:

設定exit作業ファイル
pull.rebase=false + merge.autoStash=true0競合マーカー入り
pull.rebase=true + rebase.autoStash=true0競合マーカー入り
pull.rebase=false + merge.autoStash=false1無傷 (merge を拒否)
pull.rebase=true + rebase.autoStash=false128無傷 (rebase を拒否)

git rebase 単体も同じで、pop が衝突しても Successfully rebased と exit 0 で終わる。stash は一覧に残る。

$ git -c rebase.autoStash=true rebase main; echo "rc=$?"
Created autostash: 6b17c24
Your local changes are stashed, however applying them
resulted in conflicts.  You can either resolve the conflicts
and then discard the stash with "git stash drop", or, if you
do not want to resolve them now, run "git reset --hard" and
apply the local changes later by running "git stash pop".
Successfully rebased and updated refs/heads/empty.
rc=0

--ff-only が保証するのは履歴の取り込み方だけで、stash の書き戻しはその外側にある。 スクリプトから呼んだ git も呼び出したユーザーの ~/.gitconfig を読むので、挙動に関わる設定はコマンドラインで固定する。

git -c pull.rebase=false -c pull.ff=only \
    -c rebase.autoStash=false -c merge.autoStash=false \
    -C "$dir" pull --ff-only
  • PITFALL: exit code だけで成否を見るスクリプトは、競合マーカー入りのファイルを commit して push まで進む。--ff-only と書いてあるので、読む側は安全側に倒してあると誤読する
